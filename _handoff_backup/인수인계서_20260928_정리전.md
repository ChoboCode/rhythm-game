# 1. 노트 레인 폭 70% 축소

연주 화면(노트가 내려오는 판)을 현재 크기의 70%로 줄인 작업입니다.

## 무엇을 바꿨나

`index.html`의 `layout()` 함수(2640번째 줄 부근)가 화면 크기(`W`, `H`)로부터
레인 폭(`LANE_W`)과 보드 전체 폭(`BOARD_W`)을 계산합니다. 이 계산에
**`BOARD_SCALE = .7`** 상수를 곱해서, 노트가 내려오는 보드(레인 전체)만
기존 계산값의 70% 크기가 되도록 했습니다.

```js
// index.html:2650-2656
const short = H < 560;
const wide = W >= 950 && !short;
/* 노트가 내려오는 레인(보드) 폭을 기존 계산값의 70%로 줄여 화면 좌우에 여백을 둔다 */
const BOARD_SCALE = .7;
LANE_W = Math.max(35, Math.floor((wide ? Math.min(1050, W * .54) : W - 24) * BOARD_SCALE / LANES));
BOARD_W = LANE_W * LANES;
BOARD_X = wide ? Math.round(W * .055) : Math.round((W - BOARD_W) / 2);
```

**범위를 이렇게 좁힌 이유:** 사용자에게 "게임화면 전체를 70%로 줄이기"와
"노트 레인 폭만 70%로 줄이기" 중 어느 쪽인지 확인했고, **레인 폭만**을
선택했습니다. 따라서 점수판·음반(HUD, `#playChrome`)·상단바는 그대로이고,
노트가 오가는 레인 칸과 그 아래 터치 건반(`#touchKeys`, `--board-w` /
`--board-x` CSS 변수로 보드 폭·위치를 그대로 물려받음)만 좁아집니다.

### 화면 폭에 따라 달라지는 동작
- **좁은 화면(모바일 기준, `wide`가 아닐 때)**: `BOARD_X`가
  `(W - BOARD_W) / 2`로 매번 다시 계산되므로 보드가 좁아져도 **화면
  가운데 자동으로 재정렬**되고, 좌우에 똑같은 여백이 생깁니다.
- **넓은 화면(데스크톱, `wide === true`, `W ≥ 950`)**: `BOARD_X`는
  `W * .055`로 왼쪽에 고정돼 있어서, 보드가 좁아진 만큼 **오른쪽에
  빈 공간(장식용 원근 배경)만 늘어납니다.** 오른쪽에는 원래도 앨범
  디스크·점수 패널(`.gameSide`, `left: 64%`)이 있어 겹치지는 않습니다.

## 검증한 내용

로컬 HTTP 서버(`python -m http.server`) + headless Chrome으로 실제
연습용 내장곡을 선택해 연주 화면까지 진입시킨 뒤, 캔버스를
`toDataURL()`로 캡처하고 내부 레이아웃 변수(`LANE_W`, `BOARD_W`,
`BOARD_X` 등)를 별도로 읽어 계산식과 대조했습니다.

| 화면 크기 | 분기 | BOARD_W(px) | 비율 |
|---|---|---|---|
| 1262×804 (데스크톱) | wide | 474 | 스케일 전 678 대비 **69.9%** |
| 504×804 (모바일 폭) | 좁음 | 336 | 스케일 전 480 대비 **70.0%** |

두 경우 모두 스크린샷에서 레인·판정선·터치 건반이 겹치거나 잘리지
않고, 계산대로 축소·정렬됨을 눈으로 확인했습니다. 콘솔 오류도 없었습니다.

### 확인하지 못한 부분
- 스크린샷은 연주 시작 전 **"3, 2, 1" 카운트다운** 단계라 실제로 노트가
  떨어지는 모습, 판정(PERFECT/GREAT 등), 롱노트 렌더링은 눈으로 보지
  못했습니다. 다만 이 값들은 모두 같은 `LANE_W`/`BOARD_X`를 그대로
  쓰므로 계산상 문제는 없습니다.
- `#playChrome`(점수판·음반 등 HTML 오버레이)은 `<canvas>` 밖의 별도
  DOM이라 `toDataURL()` 캡처에 잡히지 않습니다. HUD 쪽은 이번 변경과
  무관하므로 별도로 다시 찍어 보지 않았습니다.
- 실제 기기(스마트폰 등)에서의 터치 조작감, 7키 모드(`LANES === 7`)는
  코드상 같은 공식을 타므로 별 문제 없을 것으로 보이나 실기기로는
  확인하지 않았습니다.

## 조정하고 싶을 때

`layout()` 함수 안의 `BOARD_SCALE` 값 하나만 바꾸면 됩니다
(`index.html` 2653번째 줄 부근). 1보다 작으면 좁아지고, 1이면 이번
변경 이전 크기로 되돌아갑니다. `Math.max(35, …)` 최소 레인 폭 보호는
그대로 유지되므로 너무 작은 값을 넣어도 레인이 완전히 뭉개지진
않습니다.

# 2. 가사 자막 기능 추가

곡 선택 화면에서 가사를 입력하고, 노래를 들으며 탭으로 시간을 맞춰
연주 중 자막으로 보여주는 기능입니다. 음성 인식(ASR)은 쓰지 않습니다 —
가사 저작권·정확도 문제를 피하려고 **사용자가 직접 입력**하는 방식을
골랐습니다. 사용법은 `README.md`의 "가사 자막" 절에 있습니다.

## 무엇을 추가했나

- **데이터**: `S.lyrics = {title, lines:[{t, text}]}`. `lyricsKey(song)` →
  `localStorage` (`lyrics1|<곡 식별자>`), 채보(`chartKey`)와 같은 방식이지만
  난이도와는 무관합니다(`index.html`의 `readCachedChart` 바로 뒤,
  `lyricsKey`/`cacheLyrics`/`readCachedLyrics`).
- **화면**: 새 화면 `scLyrics`(가사 입력 + 탭 싱크 UI). 곡 선택 화면의
  **추가 설정 · 조작법 → [가사 자막]** 버튼으로 들어갑니다.
- **싱크 방식**: `싱크 보정`(`scCalib`)과 동일한 탭 방식을 재사용했습니다.
  `Snd.start(buffer, 0, .3)`으로 곡을 재생하고, 줄마다 버튼(또는 `Space`)을
  누른 시각(`Snd.time()`)을 그대로 타임스탬프로 씁니다. 상태는 module-level
  `lyricsSync` 객체(`running`/`done`/`lines`/`times`/`idx`)로 관리합니다.
- **표시**: `drawHud()`(매 프레임)에서 `updateLyricCaption(songT)` 호출.
  현재 시각이 `[줄의 t, 다음 줄의 t)` 구간에 들어오면 그 줄을 보여주고,
  마지막 줄은 `t + 5초`까지 보여준 뒤 사라집니다. HTML `<p id="lyricCaption">`
  요소(`#playChrome` 안, `.gameTop` 바로 아래)를 CSS `opacity` 전환으로
  켜고 끕니다 — 캔버스가 아니라 HTML 오버레이라서 노트 그리기 로직은
  건드리지 않았습니다.
- **저장/내보내기**: `[저장]`은 `localStorage`에만 남습니다. `[가사 파일로
  저장]`(`downloadLyricsFile`)은 JSON Blob을 만들어
  `<곡명>.lyrics.json`을 내려받습니다 — 다만 **`songs/songs.json`에 적어서
  자동으로 불러오게 하는 기능은 아직 없습니다.** 채보의 `"charts"` 필드처럼
  `"lyrics"` 필드를 추가해 `select()`나 `prepare()` 단계에서 fetch하도록
  확장하면 됩니다(요청받지 않아 만들지 않았습니다).
- **설정**: `prefs.showLyrics`(기본 `true`) — 연주 중 자막 표시 여부.
  `scLyrics` 화면의 **[연주 중 자막 보기]** 토글로 켜고 끕니다.

## 키 입력 관련 주의

6/7키 모드에 따라 `Space`가 레인 키(7키의 가운데 레인)일 수 있어서,
`onKeyDown`의 레인 판정보다 **먼저** `scLyrics + Space + lyricsSync.running`
조건을 가로채도록 함수 맨 앞에 넣었습니다(`싱크 보정`도 같은 이유로
비슷하게 처리돼 있습니다). 가사 입력 중(`<textarea>` 포커스)에는 이 조건이
걸리지 않아 Space로 띄어쓰기가 정상적으로 입력됩니다.

## 검증한 내용

- `node --check`로 6개 인라인 `<script>` 블록 모두 문법 오류 없음을 확인.
- 로컬 서버 + headless Chrome으로 전체 흐름(가사 입력 → 탭 싱크 완료 →
  저장 → 곡 목록으로 → 게임 시작 → 연주 화면 진입)을 자동화해 콘솔
  오류가 없음을 확인.
- 자막이 줄마다 정확한 구간에서 나타나는지는, 오디오 시계(`Snd.time()`)가
  headless(오디오 장치 없는) 환경에서 제대로 흐르지 않아 실제 재생으로는
  확인이 어려웠습니다. 대신 `updateLyricCaption(t)`를 가짜 시각 값으로
  직접 호출해 경계값(줄 시작 직전/직후, 마지막 줄 종료 시점)을 확인했고,
  `[0,2) → LINE-A`, `[2,4) → LINE-B`, `[4,9) → LINE-C`, 이후 숨김까지
  의도대로 동작함을 확인했습니다.
- `scLyrics` 화면(빈 상태·싱크 진행 중 상태) 전체 페이지 스크린샷으로
  레이아웃이 겹치거나 잘리지 않는지 모바일 폭(520px)에서 확인했습니다.

### 확인하지 못한 부분

- **실제 브라우저에서 탭 싱크의 체감 정확도**는 확인하지 못했습니다
  (headless 환경은 오디오 클록이 정상적으로 흐르지 않아 실제 사람이
  탭했을 때와 같은 조건으로 재현할 수 없었습니다). 로직 자체는 검증했지만,
  실제로 눌러 보면서 "박자에 맞춰 누르기 쉬운지"는 사람이 확인해야 합니다.
- 7키 모드에서의 `Space` 가로채기(위 "키 입력 관련 주의")는 코드 리뷰로는
  맞지만 실제 키보드로는 눌러 보지 않았습니다.
- 데스크톱(넓은 화면) 레이아웃에서 `scLyrics` 화면은 스크린샷으로 보지
  않았습니다(모바일 폭만 확인). 다만 이 화면은 새 CSS를 거의 추가하지
  않고 기존 `.screen`/`.btn`/`.chip`/`.row` 클래스를 그대로 재사용해
  다른 화면(예: `scCalib`)과 같은 반응형 규칙을 따르므로 위험은 낮다고
  판단했습니다.
- 자막 텍스트에 아주 긴 줄을 넣었을 때 화면 폭을 넘는지(줄바꿈/자르기
  처리가 없음)는 확인하지 않았습니다. 필요하면 `#lyricCaption`에
  `white-space: nowrap` 대신 자동 줄바꿈이나 `fit()`(있는 글자 자르기
  함수, `game.js` 블록에 이미 있음)을 적용할 수 있습니다.

# 3. 긴 노트가 한 구간에 몰리는 문제 수정

사용자가 "오늘부터 우리" 곡에서 긴 노트가 유난히 많게 느껴진다고 보고해
살펴본 결과, **전체 비율은 정상(NORMAL 기준 15.9%, 목표 16%)인데 특정
구간에만 몰려 있는 문제**였다. 예: NORMAL 채보 0~15초 구간에만 17개,
판정 순서로 6개가 연속으로 긴 노트인 지점이 있었음(정상 곡들은 보통
1~2개 연속).

## 원인

`ChartGen.pickHolds()`(`index.html`, chart.js 블록)가 긴 노트 후보를
**점수(소리가 이어지는 정도 등)로 정렬해 상위 N개를 그대로 뽑는 방식**이었다.
인트로의 패드 화음처럼 소리가 오래 이어지는 구간이 있으면, 그 구간의
후보들이 전부 고득점을 받아 상위 N개를 그 구간이 통째로 차지해 버린다.
전체 비율(`holdShare`)은 맞아도 실제 플레이에서는 그 구간만 긴 노트
투성이로 느껴지는 이유다.

## 무엇을 바꿨나

`pickHolds()`의 마지막 선택 단계에 **시간 간격 제한**을 추가했다
(`index.html`, `pickHolds` 함수 끝부분). 점수 순으로 훑으면서, 이미
고른 긴 노트와 `localGap`초보다 가까우면 건너뛴다.

```js
const avgGap = want > 0 ? duration / want : 0;
const localGap = Math.max(1.2, avgGap * .45);
```

`avgGap`은 "긴 노트를 곡 전체에 고르게 뿌렸다면 평균 몇 초에 하나씩
나올지"이고, 그 45%보다 가까운 재선택은 막는다(최소 1.2초는 항상 보장).
이렇게 하면 점수가 아무리 높아도 같은 구간에 계속 몰리지 못하고, 대신
다음으로 점수가 높은 **다른 시간대**의 후보가 뽑힌다. 목표 개수(`want`)를
못 채우는 경우도 있을 수 있는데(그 곡에 그만큼 퍼뜨릴 후보가 없으면),
억지로 채우지 않는다 — 다른 난이도 필터링과 같은 원칙이다.

## 검증한 내용

- `node tools/test-chart.cjs` 통과(긴 노트 비율 범위·재현성 등 기존
  안전장치 그대로 유지).
- "오늘부터 우리"를 직접 떼어내 구간별(15초 단위) 긴 노트 개수와
  "판정 순서상 연속 긴 노트 최대 개수"를 스크립트로 세어 전/후 비교:
  - NORMAL 연속 최대: 6개 → **1개**
  - NORMAL 15초 구간 최대 밀집: 17개 → **9개**
  - 전체 비율은 15.9%로 거의 그대로(수정 전후 차이 0.1%p 이내)
- 등록된 15곡(자동 생성) 전체를 다시 만들어(`tools/build-song-charts.cjs
  --write`) `node tools/test-song-library.cjs`까지 통과 확인.
- `우리 마을 축제`는 이 함수를 안 쓰는 별도 Python 채보라 영향 없음
  (그 곡은 원래 긴 노트 비율이 낮은데 길이가 전부 똑같이 고정되는 별개의
  특이점이 있음 — `tools/build-drum-charts.py` 쪽을 봐야 함, 이번에
  손대지 않았음).

### 추가: 난이도별로 다르게(유연하게)

처음엔 `localGap` 계수(`.45`, 최소 `1.2`초)를 세 난이도에 똑같이 썼는데,
사용자가 "난이도별로 다르게, 너무 빡빡하게 1개로 고정할 필요 없다"고
피드백을 줘서 `DIFF` 프리셋에 `holdGapMin`/`holdGapFrac`을 난이도마다
따로 뒀다(`index.html`, `DIFF` 객체).

```
easy:   holdGapMin: 1.6, holdGapFrac: .55   (가장 널널하게 퍼뜨림)
normal: holdGapMin: 1.0, holdGapFrac: .40
hard:   holdGapMin:  .6, holdGapFrac: .25   (가장 촘촘하게 붙어도 허용)
```

`pickHolds()`는 이제 `Math.max(preset.holdGapMin, avgGap * preset.holdGapFrac)`로
간격을 정한다. "오늘부터 우리"로 다시 확인해 보니 15초 구간 최대 밀집이
EASY 7개 · NORMAL 10개 · HARD 10개로, 쉬움일수록 더 퍼지고 어려움일수록
더 붙을 수 있게 난이도 차이가 생겼다. (판정 순서상 "연속 개수"는 세
난이도 다 여전히 최대 1인데, 이건 로직이 인접한 두 노트가 아니라 **시간
간격**으로 제한하기 때문에 — HARD처럼 초당 노트가 많으면 바로 다음 노트가
보통 간격보다 가까워서 연속 인덱스로는 잘 안 잡힐 뿐이다. 강제로 1개로
막아 둔 규칙은 아니다.)

## 확인하지 못한 부분

- `holdGapMin`/`holdGapFrac` 값은 여전히 "오늘부터 우리" 한 곡을 보고
  정한 것이라, 다른 곡·다른 템포에서 최적인지는 사람이 직접 쳐 보며
  체감을 확인하지는 못했다.
- 우리 마을 축제의 "긴 노트 길이가 전부 똑같다"는 별개 발견은 이번
  범위 밖이라 손대지 않았다. 다음에 그 곡의 긴 노트가 단조롭다는 얘기가
  나오면 `tools/build-drum-charts.py` 쪽 긴 노트 길이 산출 로직을 볼 것.

# 4. 타격음이 곡마다·구간마다 다르게, 밀도 구간 추가

사용자가 "키보드 누를 때 나는 소리가 곡마다·시간대마다 다르고 타이밍에
어울렸으면 좋겠다(지금은 따로 논다)"고 요청. 그리고 "노트가 평소보다
1.3배 더 나오는 구간도 있으면 좋겠다"고 요청.

## 원인(타격음)

`soundDrum()`(game.js 블록)은 `note.drum`이 있으면 그걸 쓰고, 없으면
**레인 번호로 고정된 표**(`['hat','snare','tom','kick','tom','snare','hat']`)를
쓴다. 그런데 자동 생성 15곡은 애초에 `note.drum`을 채운 적이 없어서
전부 레인 표 그대로 — 실제 그 순간 곡에서 무슨 소리가 났는지와 전혀
무관했다(사용자가 말한 "따로 논다"가 이것). `note.drum`을 실제로 쓰는
건 별도 Python 채보(우리 마을 축제)뿐이었다.

## 무엇을 바꿨나(타격음)

`mergeEvents()`가 이미 대역별 온셋을 하나로 합치면서 `low`/`high` 같은
힌트를 남기고 있었다(`index.html`, chart.js 블록). 여기에 **가장 세게
울린 대역 번호**(`band`, 0~4)도 같이 남기도록 했다.

```js
if (on.strength > cur.bandStrength) { cur.bandStrength = on.strength; cur.band = on.band; }
```

그리고 노트를 만드는 자리(`finish()` 안, `notes.push(...)` 직전)에서
`BAND_DRUM = ['kick','kick','snare','hat','crash']`로 대역 번호를
타격음 이름으로 바꿔 모든 노트에 `drum` 필드를 채웠다. `soundDrum()`은
손대지 않았다 — `note.drum`을 이미 최우선으로 쓰고 있었으므로, 채워
주기만 하면 자동으로 반영된다.

## 검증(타격음)

- 15곡을 전부 다시 만든 뒤 NORMAL 채보의 타격음 분포를 곡별로 세어 봤다.
  곡마다 kick/snare/hat/crash 비율이 뚜렷이 다르다(예: 입시 스트레스는 snare 156으로 스네어가
  유난히 많음, 깊은 밤은 crash 223으로 고음이 많음) — 이전에는 모든 곡이
  같은 레인 표만 썼으니 있을 수 없던 차이다.
- "오늘부터 우리" 한 곡을 30초 구간별로 쪼개 타격음 구성을 봤더니 구간마다
  kick/snare/hat/crash 비율이 계속 바뀐다(예: 0~30초는 crash가 상대적으로
  많고 60~90초는 kick 비중이 확 늘어남) — 시간대에 따라서도 달라진다는
  요청을 만족한다.
- `tap`/미분류로 빠진 노트는 15곡 전부 0개 — 전 노트가 대역 기반으로
  분류됨.

### 확인하지 못한 부분(타격음)

- **"드럼이냐 기타냐" 같은 실제 악기 종류는 구분하지 못한다.** 이 방식은
  주파수 대역(저음/중음/고음)만 보고 킥·스네어·하이햇·크래시 네 가지
  타악기풍 소리로만 매핑한다. 기타 스트로크나 신스 리드처럼 대역이
  겹치는 악기는 그냥 그 순간 가장 강한 대역에 맞는 타악기음으로
  들린다 — "가끔은 기타 형태로도"까지는 이번 범위에서 만들지 못했다.
  진짜 악기 인식을 하려면 훨씬 무거운 분석(음색 특징 추출 등)이 필요해
  가벼운 실시간 분석이라는 이 프로젝트의 전제와 부딪힌다.
- 타격음 자체(kick/snare/hat/crash 4종의 합성 사운드)는 이전 그대로다 —
  "어느 순간에 무슨 소리를 낼지"만 곡에 맞게 바꿨을 뿐, 소리 자체를
  곡에서 뽑아 쓰지는 않는다(원곡 소리를 그대로 얹으면 그 순간 원곡과
  겹쳐 울려서 오히려 이상하게 들릴 수 있어 일부러 피했다).

## 무엇을 바꿨나(밀도 구간)

`finish()`의 간격 필터링 직전에, 병합된 온셋(`events`)을 20초 폭
슬라이딩 윈도우로 훑어 **온셋이 가장 많이 몰린 20초**를 찾는다(도입부·
끝부분 8%는 제외). 그 구간에서만 `minGap`을 0.77배로, `maxNps`를 1.3배로
풀어 더 많은 후보가 살아남게 했다. 곡에 실제로 소리가 많은 자리만
골라 쓰므로 없는 노트를 억지로 만들지 않는다(다른 필터링과 같은 원칙).

## 검증(밀도 구간)

15곡을 전부 다시 만든 뒤, 각 곡의 "가장 바쁜 20초"의 초당 노트 수를
그 곡 전체 평균과 비교했다.

| 배율 | 곡 |
|---|---|
| 1.5~1.66배 | Bass Control · Last Stage · Neon Runner · System · 깊은 밤 · 두 사람의 행복을 빌어 · 시험이 끝났다 · 오늘부터 우리 · 입시 스트레스 (9곡) |
| 1.3배 못 미침 | Break It Down(1.11) · 야자 탈출(1.13) · 터뜨려라(1.15) · 하동으로가요(1.08) (4곡) |

`test-chart.cjs`의 전체 밀도 상한(`nps(hard) < 6.5` 등)은 그대로 통과.

### 확인하지 못한 부분(밀도 구간)

- 위 4곡은 목표한 1.3배에 못 미쳤다. 온셋 분포 자체가 곡 전체에 걸쳐
  비교적 고르기 때문으로 보이는데(그 구간 말고도 이미 촘촘한 곳이
  많아 "몰아줄" 여지가 적음), 강제로 더 채우려면 실제로 소리가 없는
  자리에도 노트를 놓게 되어 하지 않았다. 필요하면 `spikeLen`(20초)을
  늘리거나 배율(`* 1.3`)을 더 올려 재시도할 수 있지만, 곡 자체가 그런
  굴곡이 없다면 한계가 있다.
- 밀도 구간의 위치가 실제로 "후렴/절정"과 일치하는지는 온셋 개수로만
  추정한 것이라 확인 못 했다(예: 온셋이 단순히 많다고 항상 후렴은
  아닐 수 있음).

# 5. 한꺼번에 처리한 개선 목록 + 피버타임

이전 세션에서 정리해 둔 "추가 개선 목록"을 사용자가 "다 개선해줘"로
한 번에 요청. 아래 각 항목은 15곡 재생성이 필요한 것과 아닌 것이 섞여
있으니, 다음에 또 채보 관련 코드를 고치면 **한 번에 몰아서** 재생성할 것
(`for f in ...; do node tools/build-song-charts.cjs "songs/$f.mp3" --write; done` —
이번에 이 루프를 5번 가까이 따로 돌려서 시간을 꽤 썼다).

## 처리한 것

1. **우리 마을 축제 롱노트 길이 고정 버그** — `tools/build-drum-charts.py`의
   크래시 길이 계산이 `beat * 고정배수`라 사실상 매번 같은 값이었다.
   `event['activity']`(이미 계산해 두던 구간 활동도, 0~1)로 0.65~1.15배
   흔들어 실제로 소리가 센 순간일수록 길게 잡도록 고쳤다. 재생성 후
   길이가 0.56~0.93초(easy/normal), 0.66~1.17초(hard)로 다양해짐 확인.
   `validate-drum-charts.py`로 온셋 정합성(98% 내외)도 재확인.
2. **밀도 스파이크 4곡 미달 문제** — `spikeMinGap`을 `.77→.64`,
   `spikeNps`를 `1.3→1.5`로 더 풀었다. 미달했던 4곡 전부 1.5배 이상으로
   올라옴(자세한 수치는 4번 섹션 참고, 그 위에 이번 수치를 덮어씀).
3. **미리듣기 디코드 중복 제거** — `loadBuffer(song)`이 `prepare()`와
   `playPreview()` 양쪽에서 쓰이는데, 이제 `previewCache`에 이미 있으면
   그걸 그대로 쓰고 다시 디코드하지 않는다. 곡을 미리듣기로 들어 본 뒤
   바로 게임을 시작하면 로딩이 사실상 즉시 끝난다.
4. **BPM 확신도 개선 시도 → 되돌림.** 자기상관 최고 봉우리 하나가 아니라
   여러 봉우리에서 후보를 넓게 뽑도록 `estimateTempo()`를 고쳐 봤는데,
   재생성해 보니 서로 다른 5곡이 전부 정확히 BPM 172.3으로 수렴하는
   명백한 오탐이 나왔다(무관한 곡들이 같은 BPM일 수 없음 — 후보를
   넓힌 만큼 "격자가 촘촘할수록 유리해지는" 기존의 알려진 함정을 더
   자주 건드린 것으로 보임). 확신도 숫자 자체는 올라갔지만 실제로는
   더 나빠진 신호라 판단해 **원래 코드로 되돌렸다.** 근거 없는 곡(정답
   BPM을 모름)에서 이런 종류의 변경은 검증할 방법이 마땅치 않으니,
   다음에 다시 시도한다면 최소한 BPM을 알고 있는 곡 몇 개로 먼저
   검증하고 나서 전체에 적용할 것.
5. **피버타임 추가** — 게이지가 100에 닿으면 8초짜리 피버타임에 들어간다.
   - `P.fever`/`P.feverT`/`P.feverArmed`(재무장 조건: 게이지가 100 밑으로
     한 번 내려가야 다시 터진다)를 `loop()`에서 매 프레임 갱신.
   - 피버 중엔 실패 판정을 쉰다(`award()`의 `prefs.fail && gauge<=0` 검사에
     `&& !P.fever` 추가).
   - 점수: 피버 중 딴 판정 가중치 합(`P.feverWeightSum`)을 따로 모아
     `finalScore()`에 `900000 * feverPart * .18`만큼(즉 그 판정들의 정확도
     기여분의 18% 보너스) 더한다. 콤보 배율(3번 섹션)과는 곱해지는
     지점이 달라 — 배율은 최종 점수 전체에, 피버 보너스는 정확도
     항목에만 — 서로 상쇄되지 않고 둘 다 적용된다.
   - 이펙트: 판 테두리가 금빛으로 맥동(캔버스), 가운데에 "FEVER!" 배너가
     커지며 나타났다 사라짐, LIFE/GROOVE 막대가 금빛 그라데이션 +
     맥동 테두리로 바뀌고 숫자 대신 "FEVER" 표시, 타격 불꽃이 판정과
     무관하게 금빛으로 더 많이 튐(+5개). `prefers-reduced-motion`이면
     캔버스 쪽 맥동은 고정값으로 멈춘다(기존 전역 규칙 덕에 CSS
     애니메이션은 이미 꺼짐).

## 검증

- `tools/test-hold-combo.cjs`에 `comboMultiplier`때와 같은 이유로
  `FEVER_SCORE_BONUS`/`P.feverWeightSum`을 스코프에 추가해야 했다(또
  한 번 이 테스트가 깨졌다 — 4번 섹션 끝의 "구조적으로 신경 쓸 점" 참고).
  피버 보너스가 만점에 정확히 `900000*.18`만큼 더해지는지 어서션 추가.
- headless Chrome으로 실제 페이지에서 검증. 다만 이번엔 `연습용 내장곡`이
  없어져서 `btnStart` 클릭 후 실제 mp3 디코드+분석을 기다리는 방식이
  너무 느리고 불안정했다 — 대신 `Snd.context().createBuffer(...)`로
  5초짜리 무음 버퍼를 만들고 `S.chart`에 빈 노트 배열을 직접 넣은 뒤
  `startPlay()`를 바로 호출하는 디버그 훅(`_forcePlay`)을 임시로 추가해
  우회했다. 이 방법으로 게이지 100 도달 → 발동(`fever:true`, 클래스
  `.fever` 부여, "FEVER" 텍스트) → 8초 뒤 자연 종료(클래스 제거,
  숫자 표시 복귀)까지 전부 실제 DOM에서 확인했다. **다음에 비슷하게
  검증하려면 이 패턴을 재사용할 것** — `연습용 내장곡`이 사라진 뒤로는
  이게 사실상 유일하게 빠르고 안정적인 실측 검증 경로다.
- `test-chart.cjs`·`test-key-modes.cjs`·`test-song-library.cjs` 전부
  최종 상태로 재통과 확인.

## 확인하지 못한 부분

- 피버타임 이펙트가 실제로 눈에 거슬리지 않고 멋있게 보이는지는
  스크린샷 없이 로직만 검증했다(캔버스는 게임이 실제로 진행 중이어야
  그려지는데, 이번엔 `_forcePlay`로 빈 노트 채보를 썼기 때문에 노트
  자체가 없어 화면을 찍어도 의미가 없었다).
- 완벽하게 잘 치는(게이지가 100에서 안 떨어지는) 플레이는 피버타임이
  처음 한 번만 터지고 다시는 안 터진다(재무장 조건이 "100 밑으로
  한 번 내려가야"라서). 의도한 설계지만 실제로 이상하게 느껴지면
  재무장 문턱을 "100 밑" 대신 "몇 초 이상 100 유지 후 재사용 가능
  쿨다운" 같은 방식으로 바꿔야 할 수 있다.
- 피버 점수 보너스 배율(`.18`)과 지속시간(8초)은 감으로 정한 값이라
  실제 플레이 밸런스로 검증되지 않았다.

# 6. 곡 선택 화면 재구성 (3단 레이아웃 → 한 블록)

사용자가 이미지(참고 목업)를 주며 "왼쪽 내 최고 기록 + 가운데 트랙정보/난이도 +
오른쪽 곡 정보"로 나뉜 3단 레이아웃을 하나로 합쳐 달라고 요청. 배경·전환
화면도 곡 표지 사진을 흐리게 깐 분위기로 바꿔 달라고 함께 요청받았다.

## 무엇을 바꿨나

- `.selectionDashboard`를 3열 그리드에서 **가운데 정렬 flex 컬럼**
  (`max-width:640px`)으로 바꿨다. `.recordPanel`/`.infoPanel`/`.centerPanels`를
  없애고, 제목 → 아티스트 → 한 줄 요약(`BPM · 재생시간 · KEY · BEST`,
  `.trackMetaLine`) → 난이도 카드 순서로 쌓이는 `.trackSummary` +
  `.difficultyPanel` 두 블록만 남겼다.
- 난이도별 최고 기록 목록(`#bestRows`)과 곡 상세 정보(아티스트/조성/형식/설명)는
  **지우지 않고** 기존 `<details id="playOptions">`("추가 설정 · 조작법") 안
  `.detailBlocks`로 옮겼다. summary 문구도 "추가 설정 · 곡 정보 · 조작법"으로
  바꿔 거기 있다는 걸 알 수 있게 했다.
- `renderRecords()`가 기존처럼 `#bestRows`를 채우는 것에 더해, **현재 선택된
  난이도**의 최고 기록을 `#trackBestScore`/`#trackBestRank`(요약 줄의
  `BEST` 항목)에도 반영하도록 한 줄 추가했다. `applySelection()`의 필드
  타깃도 새 요소들로 옮겼다(`infoBpm`/`infoDuration`은 요약 줄과 중복이라
  아예 없앰).

## 검증한 내용

- headless Chrome으로 데스크톱(1400px)·모바일(390px, 실제 CDP 디바이스
  에뮬레이션 — `--window-size` CLI 플래그는 이 기기의 화면 배율(DPI) 때문에
  실제보다 좁게 렌더링되는 것처럼 보여서 오해할 뻔했다. **좁은 화면을
  검증할 땐 `Emulation.setDeviceMetricsOverride`를 쓸 것, CLI
  `--window-size`만 믿지 말 것.**) 둘 다 잘림·가로 스크롤 없음을 확인.
- `<details>`를 펼쳐 이동한 최고 기록·곡 정보가 정상적으로 보이는지
  스크린샷으로 확인.

### 확인하지 못한 부분

- 목업 이미지의 사실적인(포토그래픽) 색감·질감까지는 맞추지 않았다.
  구조(정보 통합)와 배경(7번 항목의 흐린 표지 사진) 정도만 반영했다.

# 7. 게임 시작 전환 연출 (디스크 확대 → 도착 → 레인 점등)

"게임이 시작되면 디스크가 확대되면서 게임 화면으로 가면 좋겠다"는 요청에서
시작해, 여러 차례 피드백을 거쳐 다음 순서로 정착했다.

## 최종 동작

1. `게임 시작` 클릭 → 선택된 디스크가 **그 자리에서** 커지기 시작한다
   (`beginZoomCover`). 배경은 그 곡의 표지 사진을 흐리게 깐 것(고정 그라데이션이
   아니라 실제 `song.cover`)이고, 은은하게 깜빡이는 "NOW LOADING" 문구가 따라온다.
2. 디스크가 다 커질 때까지(약 1.4초, `prefers-reduced-motion`이면 생략)는
   **화면을 절대 바꾸지 않는다** — 채보 준비가 그보다 오래 걸려도 "곡 준비 중"
   화면이 노출되지 않고 디스크 뒤에 가려진 채 끝난다(`startPlay()`를
   `async`로 만들어 `await zoomCover.growAnim.finished` 이후에만
   `show(null)`을 부르게 함).
3. 디스크가 실제 게임 화면의 레코드 자리로 줄어들며(`finishZoomCover`) 화면이
   드러난다.
4. **디스크가 도착하는 바로 그 순간**(날아가는 도중이 아니라) 노트 레인
   (`#play` 캔버스)이 형광등 켜지듯 깜박이며 나타난다(`playLaneFlicker`
   키프레임, `steps()` 타이밍이라 부드럽게 안 번지고 뚝뚝 끊기며 켜짐).
   이걸 위해 `show(null)` 시점엔 `canvas.classList`에서 `active`를 일부러
   빼 뒀다가, 디스크 착지 애니메이션의 `onfinish`에서 다시 붙인다.

## 그 외

- 전환 화면·플레이 화면 배경 모두 `--cover-art` CSS 변수(곡 표지 URL)를
  쓴다. 이 변수를 `#gameRecordStage`가 아니라 **`#stage`에** 설정하도록
  바꿔서(`updatePlayTrack()`), 상속을 통해 `.gameSide::before`(플레이
  화면 우측 패널 뒤 여백)에서도 같은 표지를 흐리게 볼 수 있게 했다 —
  노트 레인 캔버스 자체는 건드리지 않아 가독성 위험은 없다.
- `#scSong .selectAction`(게임 시작 버튼)을 `position:sticky`로 되돌렸다
  (6번 작업으로 정보 영역이 길어지면서 짧은 화면에서 버튼이 아래로
  밀려나 스크롤해야 보이는 문제가 생겼었다).

## 검증한 내용

- headless Chrome + CDP로 **프레임 단위** 타이밍을 실측했다: 클릭 직후부터
  화면 전환 전까지 `scAnalyze`가 숨겨지지 않는 것, 디스크가 도착하는
  정확한 타이밍에 캔버스 `opacity`가 0→플리커 패턴대로 바뀌는 것,
  `prefers-reduced-motion`이면 곧장 opacity 1이 되는 것을 전부
  `getAnimations()`/`getComputedStyle` 실측으로 확인했다.
- 콘솔 오류 없음.

### 확인하지 못한 부분

- 실제 사람이 보는 "느낌"(너무 빠르다/느리다, 형광등 효과가 자연스러운지)은
  이미 몇 차례 피드백을 반영해 조정했지만, 이 문서 작성 시점 기준으로
  더 조정하고 싶다는 요청이 또 있을 수 있다. 관련 상수:
  `beginZoomCover`의 grow 애니메이션 `duration`(현재 1400ms), `coverScale`
  (`Math.min(vw,vh)*0.82`), `playLaneFlicker`의 `duration`(0.9s).

# 8. NORMAL 이상 단일 노트 밀도 증가 + 레인 공백/무음 방지

"NORMAL부터는 단일 노트 수를 조금 늘려 달라"는 요청과, 별개로 "가끔
S·F·J·L 같은 특정 건반에 한참 노트가 없다"는 신고 두 가지를 처리했다.

## 밀도 증가

`DIFF.normal`/`DIFF.hard`의 `keep`(약한 온셋도 살리는 비율)과 `maxNps`
(초당 노트 상한)를 올렸다(EASY는 그대로).

```
normal: keep .85→.90, maxNps 4.1→4.6, minGap 그대로(.24)
hard:   keep .70→.78, maxNps 5.2→5.8, minGap .15→.14
```

**이 값은 index.html의 생성기 자체를 바꾼 것이라 내 음악 파일을 직접
분석할 때만 바로 적용된다.** songs/ 폴더의 29곡은 이미 만들어진
`.normal.json`/`.hard.json`을 그대로 쓰므로(6번 문단 참고 — 저장 채보만
쓰고 자동 생성 안 함) 이 값만 바꿔서는 기존 곡에 반영되지 않는다.

그래서 **기존 파일을 덮어쓰지 않고 추가하는 방식**으로 반영했다
(`node tools/build-song-charts.cjs --write`로 통째로 재생성하면 무관한
코드 변화 때문에 완전히 다른 채보가 나오는 걸 확인해서 — 예: Bass
Control HARD가 861개 → 재생성 시 765개로 오히려 줄어듦 — 이 방식은
버렸다). 임시 스크립트(`add_density_notes_v2.cjs`, 세션 종료 시 삭제함,
필요하면 아래 로직으로 다시 만들 것)로:

1. 새 설정으로 그 곡을 다시 분석해 후보 채보를 만든다.
2. 후보의 **단일 노트만** 훑어서, 기존 채보와 시간이 거의 겹치지 않고
   (±0.05초), 그 레인의 최소 간격(`laneCool`)·롱노트 점유 구간과
   충돌하지 않고, 그 순간 초당 노트 수가 이미 상한이면 건너뛰고,
   나머지만 **기존 노트에 얹는다**(기존 노트는 시간·레인·롱노트 전부
   원본 그대로).
3. "우리 마을 축제"는 별도 드럼 기반 채보(파이썬 스크립트)라 제외했다.

**한 번 실패했었다** — 첫 버전은 레인 충돌 검사가 "그 레인의 전체 노트 중
가장 늦은 시각"과만 비교하는 버그가 있어 HARD 채보에
같은 레인 노트가 겹치는 문제가 생겼다(`test-song-library.cjs`가 잡아냄).
`songs/_chart_backup_20260926/`에 있던 원본으로 되돌리고, 레인별로 정렬된
배열에서 그 시각 **바로 앞뒤 이웃**을 찾는 방식으로 고쳐 다시 실행했다.

## 검증(밀도)

- 28곡 × (normal, hard) = 56개 파일, 자체 검증(같은 레인 `.06`초 간격)
  통과 확인 후 저장. 총 1,431개 단일 노트 추가(곡·난이도별 이전/이후
  개수는 이번 세션 로그에 있음, 대략 +2~10%).
- `tools/test-*.cjs` 7개 전부 재통과.
- **원본은 `songs/_chart_backup_20260926/`에 그대로 남아 있다.** 이 폴더는
  git 관리가 안 되는 프로젝트라 이 백업이 유일한 되돌리기 수단이다 —
  지우지 말 것.

## 레인 공백/무음 방지

`layoutLanes()`(7레인 생성기)와 `KeyModes.toSix()`(6키 변환) 양쪽에
"일정 시간 이상 안 쓰인 레인이 있으면 다음 타격을 그쪽으로 강제 배정"하는
안전장치를 추가했다(각각 idleCap ≈ 2.4~2.6초). 트릴·롤 같은 모티프가
몇 레인에만 갇혀 이어지면 특정 건반이 한참 조용해지는 문제였다.

**이건 곧바로 기존 29곡에 적용된다** — 6키 변환은 저장 파일이 아니라
**연주 시작할 때마다 그 자리에서** 실행되는 로직이라, 코드를 고친 순간부터
전 곡에 적용된다(재생성 불필요).

## 검증(공백 방지)

- 여러 곡에서 "실제로 쓰이는 6키 채보"의 레인별 최대 공백을 직접
  측정하는 진단 스크립트(세션 종료 시 삭제)로 확인. 수정 전 특정 곡에서
  6초 가까이 벌어지던 레인이 수정 후 3~4초대로 줄어듦.
- 저장된 실제 `System_2_57.hard.json`을 그대로 가져와 고친
  `KeyModes.toSix()`를 돌려서, 6개 레인 전부 최대 3.2~3.8초 안에는
  반드시 한 번씩 나옴을 확인.

### 확인하지 못한 부분

- idleCap 상수(2.4~2.6초)는 "너무 길지도 짧지도 않게"라는 감으로 정한
  값이라 실제 플레이 체감으로 검증되진 않았다.
- 밀도 증가분(+2~10%)이 사람이 치기에 적당한지는 직접 쳐 봐야 안다.

# 9. 하이라이트 구간 계단 노트 (stairRun)

"기타 솔로나 음이 올라갔다 내려오는 하이라이트 구간에 계단형 단일
노트를 여러 개 넣어 재미를 더해 달라"는 요청.

## 무엇을 바꿨나

`markRuns(events)`(chart.js 블록, `layoutLanes` 바로 앞)를 새로 추가했다.
병합된 온셋을 시간 순으로 훑으면서, **가장 세게 울린 대역 번호(`band`,
0~4, 저음→고음)가 같은 방향으로 4번 이상 이어지는 구간**을 찾아
`ev.runDir`(+1 상승/−1 하강)을 표시한다. 대역 번호가 곧 "그 순간 소리가
얼마나 높은가"의 대략적인 대체 지표라, 실제 음정 추적 없이도 "음이
쭉 올라가거나 내려가는 느낌"을 근사한다.

`layoutLanes()`의 모티프 선택부에 `ev.runDir`가 있으면 무조건 새 모티프
`'stairRun'`으로 전환하도록 넣었다(진행 중이던 다른 모티프를 끊고
들어감). `stairRun`은 `stepMax` 랜덤 폭을 쓰는 기존 `stair`와 달리
**항상 한 칸씩만** 움직여 또렷한 계단 모양을 그리고, 레인 공백 방지
강제 배정(8번 문단)과 2동시 추가(`chord`)는 이 구간 동안 꺼서 모양이
흐트러지지 않게 했다. `runDir`가 끊기면 다음 박에서 평소처럼 랜덤
모티프로 복귀한다.

## 검증

- 여러 곡에서 "생성된 채보에 실제로 연속 4개 이상 한 칸씩 오르내리는
  구간이 몇 번 나오는지" 세는 진단 스크립트(세션 종료 시 삭제)로 확인
  — 곡마다 16~52회, 길이 4~7개짜리 계단이 자연스럽게 나타남.
- `tools/test-chart.cjs` 재통과(패턴 품질 지표 포함).

### 확인하지 못한 부분

- **이건 생성기 자체 변경이라, 8번 항목과 마찬가지로 기존 29곡의 저장
  채보에는 아직 반영되지 않았다.** 내 음악 파일을 직접 열 때만 바로
  적용된다. 기존 곡에도 넣고 싶다고 하면, 8번의 "추가만 하는" 방식을
  그대로 재사용하되 이번엔 **단일 노트의 레인 재배치**(같은 시각·다른
  레인)까지 허용해야 계단 모양이 제대로 살 수 있다 — 8번 스크립트는
  레인은 그대로 두고 노트만 얹는 방식이라 그대로는 못 쓴다.
- 대역 번호 기반 "상승/하강" 판정은 실제 음정(피치) 추적이 아니라
  근사치다. 저음 악기가 우연히 고음역을 세게 치는 경우 등에서는 실제
  선율과 안 맞을 수 있다.

# 10. 미리듣기 재생 구간 단축 + 빈 건반 타격음 다양화

## 미리듣기

"디스크가 돌아갈 때 미리듣기가 끝까지 재생돼서 너무 길다"는 신고로,
`startPreviewBuffer`를 **10초 재생 → 1.1초 페이드아웃 → 잠깐 쉬었다 같은
자리에서 다시 페이드인**하는 루프로 바꿨다(`schedulePreview`/`stopPreview`가
새 루프 타이머(`previewLoopTimer`)도 같이 정리하도록 함께 고침).

## 타격음 다양화

"곡 시작·중간·끝에서 건반 누를 때 나는 소리가 다 달라야 합주하는
느낌이 난다"는 요청. 킥/탐은 이미 곡의 2초 구간별 베이스 음(`songBass`)에
맞춰 다른 샘플을 썼지만, 스네어·하이햇·크래시(음정 없는 타악기)는
구간이 바뀌어도 소프트/보통/강함 세기만 바뀔 뿐 음색은 고정이었다.

`hit()`에 non-pitched 드럼용 **재생 속도(`playbackRate`) 미세 조정**을
추가했다 — 그 구간 베이스 음(`pc`, 0~11)을 ±1.4반음 범위로 매핑해
`playBuf()`에 `rate`로 넘긴다(`playBuf`에 5번째 인자 추가). 실제 음정을
붙이는 건 아니지만, 킥과 같은 화성 축 위에서 6개 건반이 함께 미세하게
움직이는 느낌을 준다.

## 검증

- `tools/test-note-audio.cjs`의 가짜 `AudioContext` mock에
  `playbackRate` 스텁이 없어서 처음엔 그대로 죽었다 — mock에
  `playbackRate:{value:1}` 추가로 고침. 스네어가 구간(베이스 음)에 따라
  재생 속도가 달라지고, 킥은 그대로(1)인지 확인하는 어서션도 새로 추가.
- headless Chrome 실제 브라우저에서 System 곡 HARD로 6개 레인 전부
  실제 키보드 이벤트로 눌러 보고 오류 없음 확인.

### 확인하지 못한 부분 — 미해결

사용자가 "System 같은 곡에서 건반을 눌러도 가끔 아무 소리가 안 난다,
다른 곡도 그런 건반이 있다"고 신고했다. 다음을 직접 확인했지만
**재현하지 못했다**:

- `Snd.hit()` 직접 호출, `Game._press()` 테스트 훅, **실제 keydown/keyup
  이벤트 dispatch** 세 경로 모두 정상적으로 오디오 버퍼가 만들어지고
  재생 스케줄이 걸림.
- kick/tom 12개 음정 전부 + snare/hat/crash, 전부 실제 소리(0이 아닌
  샘플)가 들어있음을 버퍼 내용까지 읽어서 확인.
- `System_2_57.hard.json`의 937개 노트 전부 drum/lane/시간 값 정상.
- 일시정지·창 포커스 이탈 시 눌린 키 상태를 강제로 푸는 코드가 이미
  있어서, "누른 채로 멈춰서 그 레인만 계속 무음" 경로도 이미 막혀 있음.

사용자에게 "한 번 무음이면 그 곡 끝까지 계속 무음인지, 났다 안 났다
반복하는지"를 물어봤고 **아직 답을 못 받았다**. 다음에 이어서 볼 사람은:
- **계속 무음**이라고 하면 → 어딘가 상태가 한 번 꼬여서 안 풀리는
  버그(내가 못 찾은 경로가 더 있다는 뜻)일 가능성 → `P.pressed`/
  `P.holding` 관련 코드를 더 의심할 것.
- **났다 안 났다 반복**한다고 하면 → 소리는 나는데 음량이 작아 안
  들리는 것처럼 느껴지는 문제일 가능성이 크다 → `sfxGain`(현재 `.64`)과
  드럼별 볼륨(`{kick:.84,snare:.78,hat:.72,crash:.6,tom:.75}`, 특히
  crash·hat이 낮음)을 올려 보는 게 첫 시도가 될 것.
- 아직 어느 쪽인지 몰라 실제 코드 수정은 하지 않은 상태다.

# 11. 좌우 여백 오디오 비주얼라이저

곡 선택 화면 디스크 좌우로 남는 여백에 지금 재생 중인 소리(미리듣기
포함)를 보여주는 장치를 추가했다. 세 번 정도 모양을 바꿨다 — 최종
형태만 알면 되지만, 중간 시도가 왜 버려졌는지도 남긴다.

## 최종 형태

**연주 화면에 이미 있던 오디오 미터(`drawAudioMeters()`, 캔버스에
그리는 좌우 VU미터)와 똑같은 모양·색·데이터**를 쓰기로 했다.

- 각 옆면에 **얇은 세로 막대 하나**(테두리 있는 어두운 케이스, 안에
  네모 칸이 쌓인 LED 스타일).
- 색은 연주 화면과 같은 고정 구간(칸 위치 비율 기준): 30% 이하 하늘색
  (`#4bd5f1`) → 70%까지 초록(`#91e887`) → 86%까지 금색(`#ffd76c`) →
  꼭대기 빨강(`#ff6b82`). 흰색 피크 홀드 선(`.vizPeak`)도 그대로 재현.
- 데이터는 스펙트럼이 아니라 **`Snd.musicLevels()`**(좌우 채널 RMS,
  연주 화면과 같은 함수)를 쓰고, 감쇠 곡선(빠르게 튀어오르고 천천히
  가라앉음, 피크는 더 천천히 가라앉음)도 `drawAudioMeters()`와 같은
  계수(`dt*5`/`dt*.7`/`dt*.28`)를 그대로 복사해 썼다.
- 위치·칸 수는 CSS가 아니라 **자바스크립트로 실측**한다
  (`layoutMarginViz`, module-level 변수로 끌어올려 `applySelection()`
  에서도 다시 부를 수 있게 함 — 처음 곡 목록이 비동기로 채워지기 전엔
  디스크 요소가 없어서 위치를 잴 수 없기 때문). 선택된 디스크
  (`.songBtn.on`)의 위쪽 끝에서 시작해 난이도 버튼 줄
  (`.difficultyPanel`)의 위쪽 끝까지 정확히 이어지도록 하고, 창 크기가
  바뀌면 다시 잰다.
- 화면이 넓어 여백이 넉넉할 때(`min-width:1700px`)는 카드러셀 양옆에
  디스크를 하나씩 더 보여주되(`--slot-x` 재조정), 흐림(blur 9px)을
  강하게 줘서 장식으로만 보이게 했다.

## 버려진 중간 시도

1. **12색 스펙트럼 막대**(`Snd.musicSpectrum(bars)`, 로그 스케일 주파수
   분석 함수 — 이 함수 자체는 아직 남아 있고 안 쓰일 뿐 지운 건 아님):
   무지개색 여러 막대. → "실제 장비처럼 네모 칸 쌓이는 도트 스타일로"
   피드백을 받아 폐기.
2. **12색 LED 도트**(위 스펙트럼 + 칸 쌓기): 색은 다양한데 모양이 연주
   화면 미터와 다르다는 지적 → "게임 시작하면 뜨는 비주얼라이저처럼"
   피드백을 받아 최종 형태(연주 화면과 동일)로 교체.

`musicSpectrum()` 함수는 재사용 가능성 때문에 지우지 않고 남겨 뒀다 —
지금은 아무 데서도 호출하지 않는다.

## 검증

- headless Chrome으로 1400/2000/3440(초광폭)/모바일(390, CDP 디바이스
  에뮬레이션) 전부 확인 — 잘림·겹침 없음.
- 실측 좌표 비교로 비주얼라이저 상단이 디스크 상단과, 하단이 난이도
  패널 상단과 소수점 단위로 일치함을 확인.
- 순수 UI라 게임 로직 테스트(`tools/test-*.cjs`)는 영향 없음 — 그래도
  매번 다시 돌려 전부 통과 확인.

### 확인하지 못한 부분

- 실제 음악 재생 중 좌우 채널이 다른 곡에서 좌우 막대가 다르게
  움직이는 모습은(스테레오감이 뚜렷한 곡으로) 따로 확인하지 않았다.
- `min-width:1700px` 문턱값과 여섯 번째 디스크의 `--slot-x` 값은 감으로
  정했다 — 실제 초광폭 모니터가 아닌 헤드리스 에뮬레이션으로만 확인.

# 12. "무음 건반" 재조사 + stairRun을 기존 29곡에 적용

## 무음 건반 — 추가로 확인, 여전히 미해결

사용자가 "무음인 노트를 쳐서 그런 걸 수도 있겠다"는 가설을 제시해 전
곡·전 난이도의 노트를 훑었다. **드럼 타입이 `kick/snare/hat/crash/tom`
5종 밖인 노트는 29곡 전부에서 0개였다.** 혹시 몰라 그런 경우의 대체
경로(`soundDrum`의 `'tap'` 폴백)까지 실제로 오디오 버퍼를 만들어 봤는데
그것도 소리가 실제로 들어있었다(무음 아님). **"데이터상 무음 노트가
있어서"는 아니라는 뜻이다.** 근본 원인은 여전히 못 찾았고, 10번 항목에
적어 둔 "계속 무음인지 vs 났다 안 났다 하는지" 질문의 답이 여전히 필요하다.

## stairRun을 기존 29곡(정확히는 28곡)에 적용

9번 항목에서 "생성기에만 있고 저장된 채보엔 없다"고 남겨 둔 것을
사용자가 "구현해"로 요청해 반영했다. **처음 시도는 버리고 다시 짰다** —
그 과정을 남긴다.

### 버린 시도: 드럼 종류로 대역을 거꾸로 추정

기존 노트의 `drum` 필드(kick/snare/hat/crash)를 대역 번호로 역매핑해
(`kick=.5, snare=2, hat=3, crash=4`) 9번과 같은 `markRuns` 로직을 그
위에 돌리는 방식을 먼저 시도했다. **문제**: 드럼 종류가 4가지뿐이라
같은 종류가 여러 박 이어지는 구간(예: 크래시가 계속되는 구간)이 흔한데,
"같은 대역이 이어져도 흐름을 유지한다"는 원래 로직(9번, 실시간 생성기용)
그대로 가져다 쓰니 **평탄한 구간까지 계단으로 강제 변환**되는 오탐이
너무 많았다(한 곡에서 170개나 재배정 후보가 나왔는데, 대부분 크래시만
계속되는 평탄 구간이었다). "이어져도 유지"를 "바뀔 때만 유지"로 조이니
이번엔 4개로 급감 — 순전히 드럼 라벨만으로는 진짜 오르내림을 가려낼
해상도가 없다고 판단해 이 방식은 버렸다.

### 실제로 쓴 방식: 오디오를 실제로 다시 분석

곡을 다시 디코드해 **지금 생성기(9번에서 만든 실제 `markRuns`, 진짜
온셋 대역 정보)로 새 후보 채보를 만들고**, 그 후보 안에서 "한 칸씩
단조 이동하는 연속 구간"(=생성기가 실제로 stairRun으로 그린 자리)을
찾는다. 그 구간의 **타이밍**과 가장 가까운(±0.08초) **기존 채보의
단일 노트**들을 골라, 그 노트들만 같은 방향으로 한 칸씩 계단 재배정한다.
매칭이 4개 미만이면 그 런은 포기하고, 재배정 결과가 다른 노트와
레인·시간이 충돌하면(같은 레인 최소 간격 위반) 그 런 전체를 포기한다.
**시간·홀드·타격음은 절대 바꾸지 않고 레인만 바뀐다.**

## 검증

- 28곡(우리 마을 축제 제외) × (normal, hard) = 56개 파일 전부 자체
  검증(같은 레인 `.06`초 간격) 통과 후 저장. 감지된 런 15~47개 중
  4~24개가 실제로 매칭돼 곡당 19~119개 노트가 재배정됨(총 2,783개).
- `tools/test-*.cjs` 7개 전부 재통과.
- **새 백업을 따로 만들었다**: `songs/_chart_backup_stairrun_20260926/`
  (8번 작업 이후·이번 작업 이전 상태). 8번 때 만든
  `_chart_backup_20260926/`(최초 원본, 밀도 증가 이전)도 그대로 남아있다
  — 되돌리려면 어느 시점으로 갈지에 따라 폴더를 골라야 한다.

### 확인하지 못한 부분

- 감지된 런(15~47개) 중 절반 가까이는 기존 노트와 매칭이 안 돼 버려졌다
  — 기존 채보의 노트 밀도·타이밍이 이 신규 분석과 정확히 안 맞기
  때문이다(8번에서 이미 노트를 추가해 둔 상태라 완전히 같은 조건은
  아님). 매칭률을 더 올리려면 시간 허용 오차(현재 0.08초)를 늘리는
  방법이 있지만, 너무 늘리면 엉뚱한 노트를 계단으로 바꿀 위험이 커져
  이 값을 더 건드리지 않았다.
- 재배정된 계단이 실제로 "음이 올라가고 내려가는 느낌"과 맞아떨어지는지
  귀로 들어본 것은 아니다(9번과 마찬가지로 대역 추정 자체가 근사치).

# 13. 롱노트 길이 상한 낮추기

"롱노트가 좀 많이 긴데 다 줄일 필요는 없지만 길이를 줄였으면 좋겠다"는
요청. 실제로 각 난이도의 롱노트 길이 분포를 재보니, **상위 1/4~1/3이
전부 그 난이도의 `holdMax`(생성기 상한) 바로 근처에 몰려 있었다**
(예: NORMAL은 42.9%가 1.9초 이상, 상한이 2.4초였으니 사실상 그 근처에서
계속 잘리고 있었던 것). 반대로 중앙값은 상한과 거리가 멀었다(NORMAL
중앙값 1.67초). 그래서 **"다 줄일 필요는 없다"**는 요청과 정확히 맞는
방법은 전체를 비율로 줄이는 게 아니라 **상한만 낮추는 것**이라고 판단했다.

## 무엇을 바꿨나

`DIFF` 프리셋의 `holdMax`를 낮췄다(`index.html`).

```
easy:   2.8 → 2.3
normal: 2.4 → 2.0
hard:   2.0 → 1.7
```

이건 생성기 자체 변경이라 내 음악 파일을 직접 분석할 때만 바로 적용된다.
기존 29곡(우리 마을 축제 포함 — 이번엔 단순 상한 자르기라 그 곡의 별도
생성 방식과 무관하게 적용해도 안전하다고 판단)에는, **새 상한보다 긴
롱노트만 그 상한까지 그대로 자르는** 스크립트를 돌려 반영했다. 상한보다
짧은 롱노트는 단 하나도 건드리지 않았다 — 줄이기만 하는 작업이라
다른 노트와 새로 충돌할 일도 없다(항상 더 여유가 생기는 방향이라
별도 충돌 검사도 필요 없었다).

## 검증

- 87개 파일(29곡×3난이도) 중 83개 파일에서 총 2,959개 롱노트를 잘랐다.
  자른 뒤 분포를 다시 재보니 중앙값(NORMAL 1.67초 등)은 그대로인데
  최댓값·상위 10%가 정확히 새 상한에 맞춰짐을 확인(예: NORMAL max
  2.00, p90 2.00 — 새 상한과 일치).
- `tools/test-*.cjs` 7개 전부 재통과.
- 백업: `songs/_chart_backup_holdtrim_20260926/`(이번 작업 직전 상태,
  즉 8·12번 작업은 반영되고 롱노트만 아직 안 잘린 상태).

### 확인하지 못한 부분

- 새 상한 값(2.3/2.0/1.7초)은 "적당히 줄인다"는 감으로 정한 것이라
  실제로 쳐 봤을 때 여전히 길게 느껴지는지, 혹은 너무 많이 잘렸는지는
  사람이 확인해야 한다. 더 줄이고 싶으면 `clamp` 스크립트를 다시 만들어
  같은 방식(상한만 낮추고 그 이하는 그대로 둠)으로 한 번 더 적용하면
  된다 — 매번 재생성할 필요 없이 이 방식이 제일 안전하다.

# 14. 게임에 맞는 폰트 적용

"게임에 적합한 폰트를 찾아서 적용해줘"라는 요청. 브랜드/숫자 표시용
디스플레이 폰트와, 라벨·HUD 수치용 모노스페이스 폰트를 구글 폰트에서

## 무엇을 바꿨나

- `Orbitron`(디스플레이 폰트, 영문·숫자만 있고 한글 글리프가 없다)과
  `Share Tech Mono`(모노스페이스, HUD 숫자·라벨용)를 `<link>`로 로드.

  걸 이번에 찾아서 마저 통일했다.

## 검증한 내용

# 16. 하얀 눈위의 발자국 — 롱노트를 대폭 줄여 단일 노트로 전환(실험)

## 무엇을 바꿨나

  긴 순으로 정렬해 상위 20%만 남기고 나머지는 전부 `hold:0`으로 바꿔

# 17. 결과 화면 마우스 커서 — 텍스트 캐럿 제거

"커서가 보임"의 정체로 보인다.

### 확인하지 못한 부분

  고쳤다. 다른 화면에서도 거슬리면 같은 방식으로 범위를 넓히면 된다.

# 19. 게임 시작 시 자동차 시동음 추가

"시작하면 자동차 시동거는 소리가 추가"라는 요청. 외부 효과음 파일을
새로 구하는 대신, 이미 킥/스네어/승리음 등에 쓰던 것과 같은 방식
(Web Audio로 파형을 직접 합성)으로 만들었다 — 인터넷에서 임의로
파일을 받아오지 않고, 기존 코드 패턴을 그대로 따른 것이다.

## 무엇을 바꿨나

- `audio.js`(Snd 모듈)에 `prepareEngineStart()`/`playEngineStart()`를
  추가했다. 소리는 세 구간으로 합성된다(총 1.55초).
  1. 크랭킹(0~0.42초): 스타터 모터가 빠르게 반복해서 도는 저음 펄스
  2. 점화(0.42~0.5초): 짧은 잡음 펑
  3. 회전수 하강(0.5~1.55초): 톱니파 오실레이터가 확 올랐다가
     아이들링 떨림으로 가라앉으며 서서히 잦아든다(끝부분 0.18초는
     따로 페이드아웃을 걸어 버퍼가 끊기는 클릭음이 나지 않게 했다)
- `Snd.playEngineStart()`를 `Snd`의 공개 API에 추가하고, "게임 시작"
  버튼 클릭 핸들러(`btnStart` 리스너)에서 디스크 확대 연출을 시작하는
  것과 같은 타이밍에 호출한다. 디스크가 확대→도착(레인 점등)하는
  약 2초 동안, 그리고 실제 곡 오디오는 `LEAD_ZOOM`(3.05초) 만큼
  늦게 시작되므로, 이 시동음이 곡과 겹치지 않고 단독으로 들린다.
- `playVictory()`와 같은 패턴으로 `unlock()` 이후에만 재생하고, 실패
  시 조용히 콘솔 경고만 남기도록 했다(플레이 흐름을 막지 않는다).

## 검증한 내용

- Node vm으로 `audio.js`만 떼어내 실행해 `Snd.playEngineStart()`가
  만드는 실제 파형을 검사: 길이 1.55초, 피크 0.534(클리핑 없음),

  추가 후에도 그대로 통과).

### 확인하지 못한 부분

- 실제 스피커/헤드폰으로 들었을 때 "자동차 시동 거는 소리"라는

# 20. 새 곡 4개 등록 (ITer · 거침없이 가자 (NC 다이노스) · 말하지 못한 진심 · 우린 봄이야)

"곡 몇개 더넣었어. 지금넣은곡들 이름바꿔주고. 왠만하면 지금곡들은
단일노트를 많이해서 제작 롱노트X 진득하게 쏟아지는 단일노트의
비처럼"이라는 요청. `songs/` 폴더에 mp3+표지 png만 놓여 있고
`songs.json`에는 등록되지 않은 파일 4개를 발견해서(`Iter.mp3`,
`거침없이 가자_ NC 다이노스.mp3`, `말하지못한진심.mp3`,
`우린 봄이야.mp3`), 이 4곡을 정식으로 등록하고 요청대로 롱노트
없이 단일 노트 위주로 채보를 만들었다. (`Sweet_Victory_Rush.mp3`도
미등록 상태였지만 이건 결과 화면 승리음의 원본 소스 파일이라 곡
목록에 넣지 않았다 — 표지 png가 없는 것도 이 파일만 다르다.)

## 이름을 바꾼 이유

파일명이 다른 28곡과 다른 두 가지 문제가 있었다.

- `말하지못한진심` → 표지 이미지에 실제로 박혀 있는 제목은
  "말하지 못한 진심"(과 부제 "The Truth I Couldn't Say")이라
  띄어쓰기를 표지와 맞췄다.
- `거침없이 가자_ NC 다이노스` → 표지를 보니 "거침없이 가자"라는
  곡에 프로야구 NC 다이노스 구단 로고가 들어간 응원가였다. 파일명의
  `_`는 제목과 구단명을 어색하게 이어붙인 구분자로 보여서
  "거침없이 가자 (NC 다이노스)"로 정리했다.
- `Iter` → 표지에 박힌 실제 로고는 "ITer"(대문자 T, "IT + er",
  하동여고 동아리)였다. 대소문자만 표지에 맞게 고쳤다.
- `우린 봄이야`는 원래도 깨끗해서 그대로 뒀다.

그리고 다른 28곡과 같은 `<제목>_<분>_<초>.mp3` 규칙에 맞게 실제
재생 길이를 붙여 다시 이름 붙였다(표지 png는 기존 관례대로 분_초
없이 `<제목>.png`). 예: `ITer_3_44.mp3`, `말하지 못한 진심_4_15.mp3`.

## 등록 파이프라인 (기존 28곡과 같은 방식)

기존 28곡 중 27곡이 쓰는 표준 파이프라인을 그대로 따랐다
("우리 마을 축제" 1곡만 `build-drum-charts.py` 기반의 별도
방식이라 이번엔 그쪽을 따르지 않았다 — 대다수 방식과 통일하는 쪽을
택함).

1. `ffmpeg`로 정확한 재생 길이를 재서 파일명의 분_초와 `songs.json`의
   `duration`을 일치시켰다(`tools/test-song-library.cjs`가 이 둘의
   일치를 검사한다).
2. `songs.json`에 네 곡의 기본 항목(제목·파일·표지·길이·설명·채보
   경로)을 임시 항목으로 먼저 추가했다 — `bpm`은 임시로 120을
   넣어뒀다가, 다음 단계에서 실제 감지된 값으로 교체했다.
3. `node tools/build-song-charts.cjs "songs/<파일>" --write`로
   easy/normal/hard 채보를 실제 오디오 분석으로 생성했다(다른 28곡과
   동일한 인브라우저 `ChartGen` 로직을 Node에서 그대로 실행하는
   도구). 이때 감지된 BPM(147.7 / 152 / 139.7 / 126)을 `songs.json`의
   `bpm`에도 반영해 `test-song-library.cjs`의 "목록 BPM이 다르다"
   검사를 통과시켰다.
4. `tools/build-keysound-profiles.py`와 동일한 저음 분석 알고리즘을
   재사용해 `soundBass`를 계산했다(스크립트 자체는 등록된 **모든**
   곡을 순회하며 `songs.json` 전체를 다시 쓰기 때문에, 이번엔 그
   로직만 복사해 새 4곡에만 적용하는 별도 스크립트를 짧게 만들어
   썼다 — 기존 29곡의 값은 건드리지 않기 위해서다).
5. `soundFlow`(킥/스네어/심벌 구간별 세기)는 원곡에서 드럼만 따로
   분리해야 하므로, `python -m demucs -n htdemucs --two-stems=drums`로
   네 곡의 드럼 스템을 GPU로 분리한 뒤(`tools/build-sound-flow.py`와
   동일한 분석 알고리즘을 마찬가지로 복사해) 그 드럼 스템만으로
   `soundFlow`를 계산했다. 원본 `build-sound-flow.py`도 등록된
   모든 곡의 스템이 다 있어야 돌아가는 구조라(기존 29곡의 스템은
   이미 사라진 상태), 같은 이유로 4곡 전용 스크립트를 새로 만들어
   썼다. 드럼 스템 파일은 계산이 끝난 뒤 임시 폴더째 삭제했다
   (`songs.json`에 이미 결과가 저장됐으므로 남겨둘 필요가 없다).
6. **요청대로 롱노트를 전부 단일 노트로 바꿨다**: 위 표준 생성기가
   만든 채보에도 원래 크래시 강세 등에서 드문드문 롱노트가 섞여
   나오는데, 네 곡 모두 easy/normal/hard 전 난이도에서 `hold>0`인
   노트를 전부 찾아 `hold:0`으로 바꿨다(노트 자체는 지우지 않고
   롱노트 속성만 제거 — 타이밍과 레인은 그대로라 다른 노트와 새로
   겹칠 일이 없다. 12번 항목에서 쓴 것과 같은 안전한 방식).
   - ITer: 385/625/1059개 노트 중 77/90/116개 롱노트 → 단일 노트
   - 거침없이 가자 (NC 다이노스): 335/580/880개 중 67/93/97개
   - 말하지 못한 진심: 424/655/1071개 중 63/105/118개
   - 우린 봄이야: 380/601/1012개 중 66/96/111개

## 검증한 내용

- `songs.json`을 손으로 다시 쓴 뒤 원본(작업 전 백업)과 **파싱해서
  비교**해 기존 29곡 항목이 글자 하나까지 그대로인지 확인했다

  `soundBass`/`soundFlow` 배열이 한 줄이 아니라 항목마다 여러
  줄로 풀어써져서 파일이 451줄 → 18000줄대로 불어난 걸 발견 —
  Python 도구들이 쓰는 것과 같은 압축 정규식으로 다시 한 줄로
  되돌렸다. 줄바꿈도 원본이 CRLF였는데 처음엔 LF로 저장돼 있어서
  같이 맞췄다. 최종적으로 diff에는 새로 추가한 4개 항목만 보인다).
- `tools/test-*.cjs` 7개 전부 통과 — 특히 `test-song-library.cjs`가
  "33곡 등록"으로 늘어난 것과, 파일명 분_초, `soundBass`/`soundFlow`
  길이, 레인 겹침 없음, 난이도별 밀도 증가(easy<normal<hard)까지

- 헤드리스 크롬으로 곡 목록에서 네 곡을 직접 클릭해 표지·제목·BPM·
  길이가 화면에 올바르게 나오는지 확인했다.

### 확인하지 못한 부분

- 실제로 쳐 봤을 때 "롱노트 없이 단일 노트가 비처럼 쏟아지는" 느낌이

- `soundBass`/`soundFlow`(곡별 타격음 저음·구간 다이나믹)는 알고리즘

- 곡 목록 화면의 재생 시간 표시(예: ITer가 "3:45"로 표시됨)가
  파일명의 분_초(`_3_44`, 초 단위를 버림)와 반올림 방식이 달라

  동작이 아니라 기존 표시 로직의 반올림 방식이라 손대지 않았지만,

- BPM 감지 확신도가 낮은 편이다(ITer 등 확신도 수치는 다른 28곡과
  비슷한 범위였지만 곡마다 다르다) — 박자가 흔들리는 구간이 있으면
  일부 노트 타이밍이 살짝 어긋나게 느껴질 수 있다.

# 21. 한글 표시체 재교체 (Black Han Sans → Do Hyeon) + 새 4곡 NORMAL/HARD 밀도 재조정

18번에서 적용한 `Black Han Sans`와, 20번에서 만든 새 4곡의 밀도에 대해
"제목폰트, 게임시작폰트가 좀 가독성이 안좋음. 그리고 새로추가된노래들
또한 기존의 곡들이 단일노트가 있다면 노말이상부터는 현재의 2배는되어야
됨(롱노트가없으면 쉬움)"이라는 피드백을 받았다.

## 폰트 교체

`Black Han Sans`는 획이 두꺼워서 붙어 보이는 문제가 있었다(스크린샷으로
확인). 자간이 더 트이고 획이 두꺼우면서도 뭉치지 않는 `Do Hyeon`으로
교체했다 — `--font-kr-display`가 가리키는 폰트만 바꿨으므로 이 변수를
쓰는 세 곳(`.selectHeading h2`, `.trackSummary h3`, `#scSong
.selectAction .btn.start`)에 자동으로 반영된다.

- 실제로 구글 폰트에 있는지 먼저 `curl`로 확인하고 골랐다(`Jalnan
  2`는 구글 폰트에 없어서(400 응답) 후보에서 제외했다 — 이름만 보고
  넣었으면 폰트가 아예 로드되지 않을 뻔했다).
- 헤드리스 크롬 스크린샷으로 곡 선택 화면을 다시 확인해 글자가
  또렷해진 것을 확인했다.

### 확인하지 못한 부분

- Do Hyeon도 사람마다 가독성 체감이 다를 수 있다 — 여전히 안
  좋으면 `Gothic A1`(더 차분한 고딕) 같은 대안도 고려할 수 있다.

## 새 4곡 NORMAL/HARD 밀도 2배 재조정

20번에서 등록한 4곡(ITer·거침없이 가자 (NC 다이노스)·말하지 못한
진심·우린 봄이야)은 롱노트를 전부 단일 노트로 바꿨는데, 그러면서
난이도(체감 밀도)가 낮아진 상태였다 — "롱노트가 없으면 쉽다"는
지적이 정확했다. NORMAL/HARD만(EASY는 그대로) 단일 노트 수를 늘려
보완했다.

### 어떻게 늘렸나

`index.html`의 공유 `ChartGen` 프리셋(`DIFF`)은 그대로 두고, 이번에도
재생성 스크립트 안에서 **메모리에 올린 `chart.js` 텍스트만 임시로
치환**해 실행했다(다른 27곡·이 4곡의 EASY 난이도에는 전혀 영향 없음).

1. 먼저 `DIFF.normal`/`DIFF.hard`의 `minBeat`·`minGap`·`maxNps`·`keep`만
   더 촘촘하게 바꿔 봤다 — 어느 정도는 늘었지만(HARD가 겨우 1.1~1.5배)
   한계가 있었다.
2. 원인을 보니 온셋 후보 자체가 프리셋과 무관하게 하나의 고정 문턱값
   (`pickOnsets(...,.09,...)`, 지역평균×1.55+.012)으로 미리 뽑혀 있어서,
   난이도 프리셋을 아무리 완화해도 "뽑아 둔 후보"가 부족하면 더 늘지
   않는 구조였다. 이 공용 문턱값도 후보가 더 나오도록 같이 낮췄다
   (`.09`→`.05`, `1.55+.012`→`1.15+.006`).
3. 더 밀어붙여 봤더니(문턱을 더 낮추고 프리셋을 극단으로) 오히려 일부
   곡은 노트 수가 줄어드는 역효과가 났다(예: "거침없이 가자"가 HARD
   1822→1517로 감소) — 너무 민감해지면 잡음성 온셋이 박자 추정·격자
   스냅을 흔들어 되레 병합/탈락이 늘어나는 것으로 보였다. 그 직전
   단계(문턱 완화는 하되 그 이상은 넘지 않은 지점)로 되돌려 최종값으로
   삼았다 — 실제 소리에 안 붙는 노트를 늘리기보다, 이 지점에서
   멈추는 게 "여전히 실제 온셋에만 노트를 붙인다"는 생성기 설계
   원칙에 맞는다고 판단했다.

### 최종 결과 (기존 20번 작업 기준 대비 배율)

| 곡 | NORMAL | HARD |
|---|---|---|
| ITer | 625→1112 (×1.78) | 1059→1461 (×1.38) |
| 거침없이 가자 (NC 다이노스) | 580→1051 (×1.81) | 880→1822 (×2.07) |
| 말하지 못한 진심 | 655→1225 (×1.87) | 1071→1645 (×1.54) |
| 우린 봄이야 | 601→1169 (×1.95) | 1012→1308 (×1.29) |

있지만(특히 우린 봄이야·ITer의 HARD), 실제 온셋 재료가 그 곡에서

# 22. 새 4곡에 동시치기(2~3개 동시 노트) 추가

"좋은데 항상 단일노트가오면 동시에 1개만있는데 뭐 얘를들어 d, k 를
동시에 누른다덩가 동시에 2~3개노트를 하는 것을 추가해서 난이도를
좀더 올리는것도좋을듯"이라는 요청. 20~21번에서 만든 새 4곡의
NORMAL/HARD를 확인해 보니, 생성기에 원래 "2동시" 기능(`preset.chord`)이
있긴 했지만 실제로는 거의 안 나오고 있었다.

## 원인

생성기의 동시치기 조건이 `ev.strength > 1.6 && gap >= preset.laneCool`
인데, 21번에서 밀도를 2배 가까이 올리면서 노트 사이 평균 간격이
`laneCool`(NORMAL .24초·HARD .16초)보다 짧아지는 경우가 대부분이 돼
버렸다. 그래서 `preset.chord` 확률 자체(NORMAL .07·HARD .16)와 무관하게
"동시치기 조건을 만족하는 순간"이 애초에 드물었던 것 — 실제로 재보니
NORMAL은 1000개가 넘는 노트 중 동시치기가 단 2쌍뿐이었다.

## 무엇을 바꿨나

이번에도 `index.html`의 공유 생성기 코드는 그대로 두고, 재생성
스크립트 안에서 메모리에 올린 `chart.js` 텍스트만 임시로 고쳐 썼다
(다른 27곡·이 4곡의 EASY 난이도는 전혀 영향 없음).

- 동시치기 조건을 완화했다: 세기 문턱 1.6→1.2, 간격 조건
  `gap >= laneCool`→`gap >= laneCool*.5`, 반대손 레인의 휴식 요구량도
  `need`→`need*.7`로 낮췄다.
- 확률(`chord`)도 올렸다: NORMAL .07→.18, HARD .16→.28.
- **3개 동시**를 새로 추가했다: 아주 센 타격(`strength > 2.0`)에서
  드물게(`chord*.45` 확률) 이미 고른 2동시 자리에 엄지(`CENTER`, 스페이스바)
  까지 더해 3번째 노트를 얹는다. 좌우 양손 + 엄지 조합이라 실제로
  세 손가락으로 누르기 가장 편한 조합을 골랐다.
  - 6키 모드에서는 `CENTER`(레인 3)가 `KeyModes.toSix`에서 원래
    빠지는 레인이라, 3동시는 자동으로 2동시로 줄어든다(7키 모드에서만
    진짜 3동시). 의도한 그대로의 자연스러운 동작이라 손대지 않았다.

# 23. 동시치기 빈도를 기존 29곡 기준으로 다시 맞춤

"다른노래에도 있는지참고. 그리고 gpt랑 협업중이니 참고해주고"라는
요청. 22번에서 만든 동시치기가 기존 곡들과 비교했을 때 적당한
수준인지 실제로 세어서 확인했다.

## 조사 결과 — 기존 29곡에는 원래도 동시치기가 있었다

기존 27곡(+우리 마을 축제 포함 29곡) **전부**가 이미 생성기 자체
"2동시" 기능(`preset.chord`)으로 동시치기를 갖고 있었다 — 처음부터
있던 기능이었는데 22번에서야 실제로 통계를 내 봤다.

- 기존 29곡 NORMAL 평균: 노트의 **4.76%**가 동시치기
- 기존 29곡 HARD 평균: 노트의 **18.02%**가 동시치기
- 3동시(트리플)는 거의 없다 — 유일하게 "우리 마을 축제"에만 있는데
  이 곡은 `build-drum-charts.py`라는 완전히 다른 생성기를 쓰기
  때문이고, 공용 `ChartGen`의 동시치기 기능 자체에는 원래 3동시가
  없었다(22번에서 내가 새로 추가한 것).

이 기준과 비교하면, 22번에서 만든 새 4곡의 HARD(약 15.6~17.7%)는
**기존 평균(18.02%)과 이미 잘 맞았지만**, NORMAL(약 10.9~12.5%)은
기존 평균(4.76%)의 **2배가 넘게** 높았다 — 21번에서 밀도를 올리며
동시치기 조건(`gap >= laneCool` 등)을 완화한 게 확률(`chord`)값과는
별개로 결과 비율을 밀어올린 효과가 있었던 것.

## 무엇을 바꿨나

NORMAL의 `chord` 확률만 22번에서 올렸던 .18에서 **원래 값 .07로
되돌리고**, HARD는 이미 기존 평균과 맞아서 그대로 뒀다. 동시치기가
"발동할 수 있는 조건"(세기 문턱·간격 조건 완화, 3동시 추가)은
그대로 유지했다 — 이 조건들까지 원래대로 되돌리면 21번에서 확인한
대로 밀도가 오른 만큼 동시치기가 다시 거의 안 나오기 때문이다.

재조정 결과 NORMAL 동시치기 비율: ITer 10.1%, 거침없이 가자 7.9%,
말하지 못한 진심 8.4%, 우린 봄이야 9.9% — 기존 평균(4.76%)보다는
여전히 높지만 22번의 절반 정도로 낮아졌다. 이 정도는 "롱노트가
없는 만큼 난이도를 더 준다"는 애초 요청과도 맞는 의도적인 차이로
보고 그대로 뒀다 — 완전히 4.76%에 맞추려면 발동 조건 자체를 더
조여야 하는데, 그러면 21번에서 겪었던 것처럼 과도하게 조이다
역효과(온셋 수 자체가 줄어듦)가 날 위험이 있어 여기서 멈췄다.

# 25. 홈 화면 "F 내 음악 파일 열기" 기능 삭제

"홈화면에서 F 내음악파일열기 기능 삭제요청"이라는 요청.

## 무엇을 바꿨나

버튼 하나만 지운 게 아니라 "내 파일을 불러와 연주한다"는 기능
전체를 지웠다 — 버튼과 단축키(F)만 없애고 끌어다 놓기(drag&drop)를
남겨두면, 안내 문구도 단축키도 없이 파일을 끌어다 놓으면 몰래
동작하는 반쪽짜리 기능이 남기 때문에 일관되게 다 지웠다.

- HTML: 곡 선택 화면 헤더의 `.importArea`(버튼 + `<input type="file">`)
  삭제, 하단 단축키 안내에서 "F 내 음악 파일 열기" 문구 삭제,
  끌어다 놓기 안내(`#dropHint`) 삭제.
- CSS: `.importArea`/`.importButton`/`#dropHint` 관련 규칙과, 반응형
  미디어쿼리 안의 관련 오버라이드 전부 삭제. `#libraryStatus`(곡
  목록을 못 읽었을 때만 보이는 안내문)는 남기고 최소한의 자체
  스타일을 새로 줬다(이전엔 `.importArea` 안에 있어서 그 부모의
  레이아웃에 얹혀 있었다).
- JS: `KeyF` 단축키 처리, `fileInput`의 `change` 리스너, 문서
  전체의 `dragenter/dragover/dragleave/drop` 리스너, 그리고 이걸
  실제로 곡 목록에 추가하던 `acceptFiles()` 함수까지 전부 삭제했다
  (삭제 후 이 함수를 부르는 곳이 하나도 안 남아 안전하게 지울 수
  있었다).
- `libraryStatus`의 안내문 두 곳에서 "내 음악 파일 열기를
  이용하세요" 같은, 이제는 존재하지 않는 기능을 가리키던 문구를
  지웠다.
- **건드리지 않은 것**: `song.kind === 'file'`을 체크하는 자잘한
  분기(곡 부제 표시, 아티스트 표시 등 5곳 정도)는 그대로 뒀다.
  `acceptFiles`가 없어졌으니 이제 `kind:'file'`인 곡은 절대 생기지
  않아 이 분기들은 도달 불가능한 죽은 코드가 됐지만, 여러 곳에
  흩어진 자잘한 삼항연산자라 억지로 손대면 오히려 실수할 위험이
  더 크다고 판단해 남겨뒀다. 문제 되면 나중에 정리하면 된다.

# 26. "노래 마무리 노트 무음" 조사 — 재현 실패, 대안 원인 발견

"모든노래에서 마무리에 내려오는 노트들은 무음인데 개선요청"이라는
요청. 이전 세션부터 이어진 "특정 건반 무음" 미해결 이슈에 새로운
단서("곡 마무리"라는 구체적 타이밍)가 붙은 것이라 판단해, 이번엔
실제 게임 플레이를 헤드리스 브라우저로 끝까지 재현해 봤다.

## 무엇을 확인했나

1. **`Snd.hit()` 자체는 결백하다.** Node vm으로 `audio.js`만 떼어내
   t=5(중간)부터 t=곡길이+5(끝나고도 한참 뒤)까지 모든 구간에서
   `hit()`을 직접 호출해 실제로 만들어지는 오디오 버퍼를 검사했다 —
   전부 유효한 피크값의 실제 소리였다. 곡 마무리 근처라고 무음
   버퍼가 나오는 경우는 없었다.
2. **실제 플레이를 끝까지 재현해 봤다.** 헤드리스 크롬에서 가장
   짧은 곡("우리 마을 축제", 170초)을 7키 모드로 골라 실제로
   시작하고, `AudioBufferSourceNode.start()`를 몽키패치해 모든
   효과음 재생을 기록하면서, 곡의 마지막 10초에 들어 있는 노트
   20개(마지막 노트 포함) 전부를 실제 시각에 맞춰 실제
   `KeyboardEvent`로 눌러 봤다.
   - **처음 시도에서 뜻밖의 단서를 발견했다**: 중간 노트들을 하나도
     안 누르고 건너뛰었더니, 게이지가 바닥나 `게이지가 바닥났습니다`
     로 곡이 도중에 자동 종료돼 있었다 — 그 뒤로는 마지막 노트를
     눌러도 화면이 이미 `play`가 아니어서 아무 반응이 없었다(정상
     동작. 버그 아님). 겉보기엔 "마무리 노트가 무음"인 것과 완전히
     똑같은 증상이었다.
   - **게이지 실패를 끄고 다시 해 보니**, 마지막 10초의 노트
     20개 전부(마지막 노트 t=169.69, 곡 길이 170.11 포함) 하나도
     빠짐없이 PERFECT 판정 + 실제 오디오 재생이 확인됐다.

## 결론 (확정은 아님)

`hit()` 자체에는 문제가 없다. 대신 아주 유력한 대안 가설을 찾았다:
**게이지가 딱 곡의 클라이맥스 근처에서 바닥나 게임이 조기 종료되고,
그 순간 화면에 남아 있던 노트들이 "무음"으로 보이는 것**일 가능성이
높다. 채보 생성기가 "곡에서 가장 바쁜 20초 구간"을 자동으로 찾아
노트를 1.3배 더 채우는 기능이 있는데, 많은 곡에서 이 "가장 바쁜
구간"이 곡의 후반부(마지막 후렴·아웃트로)에 걸리기 쉽다 — 그래서
"마무리 부분에서" 게이지가 위태로워지고, 하필 그 타이밍에 실패하면
사용자 입장에서는 "곡이 끝나갈 때 노트가 갑자기 무음이 됐다"처럼
느껴질 수 있다.

## 사용자 확인 결과 — 게이지 실패 가설은 아니었다

사용자에게 물어봤다: "게임 화면은 그대로인데 소리만 안 난다"는
답을 받았다. 즉 위의 게이지 조기 종료 가설은 **틀렸다** — 결과
화면으로 안 바뀌고 화면은 정상적으로 계속 진행된다는 뜻이므로,
`press()`가 `S.screen !== 'play'`에 걸려 조용히 무시되는 상황이
아니다. 진짜 오디오(혹은 판정) 버그라는 뜻이다.

## 2차 조사 — 여전히 재현 실패

같은 방식으로 한 번 더 실제 플레이를 재현했다. 이번엔 곡 선택
클릭이 의도한 곡("야자 탈출")을 못 찾아서(추정: `img.alt` 텍스트가
기대한 형식이 아니었거나 타이밍 문제) 실제로는 기본 선택곡
("Bass Control", 표준 `ChartGen` 스키마 — 1차 조사 때 쓴 "우리 마을
축제"와 달리 특수 파이썬 생성기가 아닌 일반 곡)이 테스트됐다.
그 대신 **기본값인 6키 모드**로 처음 테스트해 본 셈이 됐다(1차는
7키 모드였다) — `KeyModes.toSix()`를 직접 호출해 실제 6키 변환
후 레인으로 정확히 매핑해서 눌렀다.

결과: 마지막 10초 노트 20개(마지막 노트 t=169.69, 곡 길이 170.11
포함) 전부 PERFECT 판정 + 실제 오디오 재생 확인. 6키 모드에서도,
표준 스키마 곡에서도 재현되지 않았다.

## 남은 가설 — 약한 기기 환경 문제일 가능성

`hit()` 자체, 판정 로직, 화면 전환 로직 모두 이 개발 PC의 일반
크롬에서는 문제가 없다. 프로젝트 메모리에 이미 "활동 페이지는
저사양(그래픽카드 없는 학교 기기) 대상"이라는 원칙이 있는데, 이번
세션에서 밀도·동시치기를 상당히 올려서(22~24번) 한 번에 겹치는
효과음 노드 수가 예전보다 훨씬 많아졌다. 저사양 기기에서 오래
연주할수록(="마무리"에 가까울수록) 쌓인 오디오 노드·GC 부담이
커져 새 노드 생성/재생이 조용히 실패하거나 지연될 가능성은 이
개발 PC로는 재현·검증할 수 없다.

### 확인하지 못한 부분 — 추가 정보가 필요하다

이 시점에서 코드 조사만으로 더 진전이 어렵다. 다음 정보를 주면

# 27. 가사 동기화 전체 재점검 — 실제 보컬과 대조해 어긋난 줄 교정

"가사를 배치하고 했는데 여전히 싱크가 안맞는 부분들이 있음. 이를
다시 꼼꼼하게 모든곡을 점검해줘"라는 요청. 가사는 `songs/*.lyrics.json`
30개 파일(29곡+1, 총 1572줄)에 저장돼 있고, 각 파일에 이미
`"timing": "audio-aligned ASR; lines marked estimated were interpolated
between recognized vocals"`라는 메타데이터가 있었다 — 즉 원래 ASR(음성
인식)로 오디오에 맞춰 만든 것이고, ASR이 못 알아들은 230줄은
"estimated"로 표시해 보간(guess)으로 채워 둔 상태였다. 이 프로젝트에
`faster-whisper`가 이미 설치돼 있어서, 같은 방식으로 실제 오디오를
다시 분석해 대조하는 파이프라인을 만들었다.

## 파이프라인

1. **보컬 분리**: `python -m demucs --two-stems=vocals`로 가사가 있는
   30곡 전부의 보컬만 GPU로 분리했다(반주가 섞이면 ASR 정확도가
   떨어지므로).
2. **재전사**: 분리된 보컬 각각을 `faster-whisper`(small, CPU)로 다시
   전사해 단어 단위 타임스탬프를 얻었다(CUDA는 `cublas64_12.dll`
   버전 불일치로 실패해 CPU로 전환 — 곡당 약 20~50초, 30곡에 15분
   정도 걸렸다. 이 사이 진행 상황을 여러 번 보고했다).
3. **대조**: 저장된 각 가사 줄의 텍스트를, 그 줄의 원래 시각 근처에서
   실제로 인식된 단어들과 문자 단위로 비교해(공백 등 제거 후
   `difflib` 유사도) 가장 잘 맞는 구간을 찾고, 그 구간의 실제 시각과
   저장된 시각의 차이를 확인했다.

## 처음 시도에서 발견한 함정과 수정

- **반복 가사 오매칭**: 검색 범위를 처음엔 ±8초로 넉넉하게 잡았더니,
  같은 후렴구가 여러 번 반복되는 곡에서 "지금 줄"이 아니라 몇 초
  떨어진 **다른 반복 지점**에 잘못 매칭되는 사례가 나왔다(예:
  Bass Control에서 7초 넘게 어긋난 "교정"이 여럿 나왔는데, 확인해보니
  같은 후렴구의 다른 반복 지점에 매칭된 것이었다). → 검색 범위를
  측정값 있는 줄은 ±3초, "estimated"(보간) 줄만 ±6초로 좁히고, 자동
  적용 가능한 최대 이동량도 각각 2.5초/5초로 제한했다. 이 범위를
  넘는 불일치는 자동 적용하지 않고 "저신뢰 불일치"로만 보고한다.
- **교정 후 순서 역전 버그**: 어떤 줄을 교정하지 않고 그대로 둘 때,
  그 줄의 "현재 시각"을 순서 검사에 반영하지 않는 버그가 있어서
  드물게(5곡) 교정된 줄이 그 다음의 안 바뀐 줄보다 시각이 앞서가는
  경우가 생겼다. 전체 30곡을 다시 검증해 잡아내고 고쳤다 — 고친 뒤
  30곡 전부 시간순 정렬 검증을 통과했다.
- 두 문제 모두 한 번 교정을 적용해 보고 나서 스스로 검증하다가
  발견한 것이라, 발견 즉시 백업에서 되돌리고 다시 만들었다(최종
  결과만 파일에 남아 있고, 중간의 잘못된 시도는 없다).

## 최종 결과

- 30곡 1572줄 중 **338줄을 교정**하고(대부분 0.5~2초 사이의 작은

  보고만** 했고, **420줄은 근처에서 맞는 보컬을 아예 못 찾아
  확인 불가**로 남겼다(위 안전장치들 때문에 사람이 봐야 할 정도로
  애매한 경우는 억지로 건드리지 않았다).
- "Neon Runner"는 유독 전멸(73줄 중 교정 0, 확인불가 73) —
  분리된 보컬 자체의 소리 레벨은 정상인데 ASR이 거의 아무것도
  인식하지 못했다(VAD 켜고/꺼도 마찬가지, 꺼니까 오히려 "1, 2, 3!"을
  반복하는 환각 증상까지 나왔다). 이 곡은 보컬이 전자음 가공이
  심하거나 ASR이 다루기 어려운 스타일일 가능성이 높다 — 이 곡만은
  사람이 직접 들으며 확인해야 한다.
- 전체 리포트는 `가사_동기화_점검_리포트.txt`(프로젝트 루트)에
  곡별로 남겨뒀다 — 교정한 줄/확인 못한 줄/저신뢰로 보류한 줄이
  전부 기록돼 있어서, 어느 곡의 어느 줄을 왜 그렇게 처리했는지
  전부 추적할 수 있다.
- 교정된 줄에는 `"resynced": true` 표시를 남겼고(어떤 줄이 이번에
  바뀌었는지 나중에 구분 가능), 기존 `"estimated": true` 표시는
  실제 오디오로 확인됐으니 지웠다. 교정된 줄의 `words`(단어별
  세부 타임스탬프)는 새 시각과 더는 안 맞으므로 오해를 막기 위해
  지웠다(줄 단위 `t`/`end`는 유지).

- **420줄(약 27%)은 여전히 확인 불가 상태다** — ASR이 그 근처에서

  맞을 수도 있다. 특히 "Neon Runner"는 사실상 전혀 검증되지 않았다.
- 338건의 교정도 어디까지나 "ASR과 텍스트가 잘 맞고 이동량이
  안전 범위 안"이라는 기준으로 자동 적용한 것이지, 사람이 귀로
  들으며 하나하나 확인한 것은 아니다 — 표본으로 여러 곡을 훑어봤을
  때는 품질이 좋아 보였지만, 실제 플레이하면서 노래를 들어봐야
  최종 확인이 된다.
- ASR 자체도 완벽하지 않다(예: "Loseit"처럼 여러 단어를 하나로
  잘못 붙여 인식하는 경우가 흔했다) — `difflib` 유사도 방식이 이런
  오류에는 어느 정도 강하지만, 텍스트가 원래 가사와 많이 다르게
  잘못 인식된 경우는 애초에 매칭 자체가 안 됐을 수 있다(그래서
  "확인 불가"로 많이 빠졌을 가능성).

# 28. "우리 마을 축제" 여전히 안 맞음 — 연속 구간 통짜 밀림 + 27번 작업이 남긴 겹침 버그 발견

27번 작업 이후 "우리마을 축제와 가사 싱크가 안맞음"이라는 재지적을
받았다. 이 곡만 따로 다시 파봤다.

## 원인 1 — 한 줄씩만 고치는 안전장치가 "통째로 밀린 구간"은 못 고친다

27번의 자동 교정은 "이 줄 하나만 옮겼을 때 바로 앞/뒤 줄과 순서가
안 엉키는지"만 봤다. 그런데 이 곡의 도입부(13.8~19.26초 구간, "붉은
리본 바람에 펄럭" / "금빛 장식 발끝에 반짝" / "한 칸 두 칸 뛰어 올라"
/ "웃음소리 번져 가" 네 줄)는 **네 줄이 통째로 뒤로 밀려 있었다** —
한 줄만 고치려 하면 아직 안 고쳐진 다음 줄의 원래 자리와 부딪혀서
"순서 역전으로 보류"됐고, 그 결과 이 네 줄은 27번 리포트에
"확인불가"나 "보류"로만 남고 실제로는 고쳐지지 않았다.

이번엔 이 곡만 다시 보컬 분리+전사해서 실제 타이밍을 직접 확인하고
(예: "붉은 리본 바람에 펄럭"은 저장된 값 13.80초가 아니라 실제로는
16.64초에 나옴), 네 줄을 한 번에 손으로 재배치했다. 넷 다 서로
순서가 맞고 앞뒤 줄과도 안 겹치는 것을 확인한 뒤 반영했다 —
자동 스크립트의 "한 줄씩만" 제약을 우회한, 이 곡 전용 수동 수정이다.

## 원인 2 — 더 심각한 발견: 27번 교정이 다른 곡들에 겹침을 만들어 놨었다

이 곡을 고치다가 우연히 "고친 줄의 end 시각이 다음 줄의 시작 시각을
넘어서는" 겹침을 발견했다. 원래 데이터(27번 작업 전 백업)에는 이런
겹침이 **0건**이었는데, 27번의 자동 교정 스크립트가 `t`(시작 시각)
순서만 검사하고 `end`(끝 시각)는 검사하지 않아서, 교정된 줄의 끝
시각이 다음 줄 시작을 넘어서는 경우를 그대로 저장해 버렸다. 전체
30곡을 다시 검사해 보니 **26개 파일에 99건**이나 있었다.

- 모든 파일에서 "어떤 줄의 end가 다음 줄의 t를 넘으면, 그 end를
  다음 줄 t 바로 앞까지 줄인다"는 규칙으로 일괄 정리했다.
- 이 과정에서 `words`(단어별 세부 타임스탬프)가 있는 줄 중 마지막
  단어의 end가 줄어든 새 end보다 커진 경우가 7개 파일 14곳
  있었는데, 이건 `tools/test-song-library.cjs`가 이미 갖고 있던
  "단어 시각이 줄 시각 범위를 벗어나면 안 된다"는 검증에 정확히
  걸렸다 — 이 테스트를 이번에 처음 끝까지 돌려보고서야 존재를
  제대로 확인했다(27번 때는 "가사 테스트는 없다"고 잘못 판단하고
  건너뛴 부분). 해당 줄들은 `words`를 통째로 지워 해결했다(어차피
  줄 끝이 줄어들면 예전 단어별 타이밍은 못 믿을 데이터가 된다).

### 확인하지 못한 부분

# 29. "우리 마을 축제" 1번째 줄("어서 와") 재조사 — 근거는 남겼지만 확신은 낮음

28번 이후 "간주하고 어서와 부터 잘안맞음"이라는 재지적을 받아, 첫
줄("어서 와, 시작 버튼을 눌러")만 다시 깊게 팠다.

## 확실하게 고친 것 — 끝나는 시각이 너무 빨랐다

이 줄의 저장된 `end`가 10.84초였는데, 두 번의 독립된 ASR 실행 모두
이 구간의 노래가 실제로는 11.50~11.54초까지 이어진다고 일관되게
알려줬다(반면 다음 줄은 11.36초에 시작). 즉 자막이 실제 노래보다
**0.7초 먼저 사라졌다가** 다음 줄이 뜨는 빈 틈이 있었다 — 이건 두
번 다 같은 값이 나온 확실한 근거라 바로 고쳤다(`end: 10.84 → 11.34`,
다음 줄 시작 직전까지).

## 애매하게 고친 것 — 시작 시각은 근거가 엇갈렸다

"시작"되는 시각(`t`)은 확신이 낮다. 조사한 내용을 그대로 남긴다.

- 분리된 보컬 트랙의 에너지를 훑어보니 7초까지는 거의 무음이다가
  **8.0~8.1초에서 에너지가 크게 뛴다** — 저장된 시작 시각 9.52초보다
  1.5초 가까이 이르다.
- 그런데 8.0~8.1초 구간의 스펙트럼을 보면 고음(4kHz 이상)에
  치우쳐 있어서, 실제 노래(포먼트가 있는 목소리)라기보다 심벌 같은
  타악기가 보컬 분리 과정에서 섞여 들어온 소리처럼도 보였다. 다만
  "시작"이라는 단어 자체에 "ㅅ" 파열음이 있어서 그 음절이라도
  고음으로 잡혔을 가능성도 배제 못 한다.
- ASR(음성 인식)은 두 번 다 9.52초에서만 처음으로 알아들을 수 있는
  단어("시작부터는 흘러" — 저장된 "시작 버튼을 눌러"와 비슷하게
  들리는 오인식)를 찾았고, 그 전(8.0~9.52초)에서는 아무것도
  인식하지 못했다.
- 실제 채보(드럼 온셋, 이 곡만 다른 생성기를 쓰지만 이건 타악기라
  가사와는 무관하게 신뢰 가능한 데이터)를 보니, 간주에서 노래로
  넘어가는 크래시+킥 그루브 자체는 6.26초에 이미 시작돼 있었다 —
  즉 "간주가 끝나는 지점"은 6.26초 근처이고, 사람 목소리는 그보다
  더 뒤에 들어온다는 것만 확인했다.

**최종 판단**: "어서 와,"(짧은 도입 소절)가 8.0초에 시작해서
"시작 버튼을 눌러"로 이어져 9.52초부터는 ASR도 알아듣기 시작한다는
해석이 가장 앞뒤가 맞는다고 보고 `t: 9.52 → 8.0`으로 고쳤다. 하지만
이건 위 여러 단서를 종합한 추정이지, 27·28번처럼 ASR 텍스트가
정확히 일치해서 확신할 수 있는 종류의 교정은 아니다.

### 확인하지 못한 부분 — 이번엔 특히 확신이 낮다

- 시작 시각(8.0초)이 맞는지는 사람이 직접 들어봐야 한다. 만약 여전히
  안 맞으면, "더 빠르게/더 느리게 나와야 한다"와 대략 몇 초 정도
  차이 나는지만 알려주면 — 이번처럼 처음부터 다시 파지 않고 바로
  그만큼 옮겨서 확인할 수 있다.
- 이번 조사에 쓴 보컬 분리+ASR+스펙트럼 분석 자체가 "시작 순간"처럼
  아주 미세한 타이밍에는 한계가 있다는 것도 확인했다 — 애매한
  값(스펙트럼 고음 편중처럼)이 겹치면 결론이 흔들릴 수 있다는 뜻이라,
  이런 미세 조정은 결국 사람이 귀로 확인하는 게 가장 확실하다.

# 30. 대조 알고리즘 전면 재설계(순차 정렬) + 30곡 재점검 + Bass Control 정밀 감사

"bass control도 안맞음. 모든곡들 한줄한줄 검토"라는 요청. 27번의
자동 대조 알고리즘 자체에 구조적 한계가 있다고 보고 알고리즘을
다시 설계했다.

## 27번 알고리즘의 한계

27번은 각 줄을 **자기 원래 시각 근처(±3~6초)에서만** 찾았다. 이 방식은
두 가지를 절대 못 고친다.
- **반복되는 후렴구**: 같은 문장이 여러 번 나오면, 몇 초 떨어진
  "다른 반복"에 잘못 물릴 수 있다(Bass Control 최초 시도에서 겪음).
- **통째로 밀린 구간**: 연속된 여러 줄이 한�런에 밀려 있으면, 한
  줄만 옮기려 해도 아직 안 옮긴 다음 줄과 부딪혀 보류된다("우리
  마을 축제" 도입부에서 겪음).

## 새 알고리즘 — 순차 포인터 방식

이번엔 시간 창을 아예 없애고, ASR 단어열을 **처음부터 끝까지 한
번만 훑는 포인터**로 바꿨다. 원리는 한 문장: *"각 줄은 이전 줄이
찾은 지점보다 뒤에서만 다음 매칭을 찾는다."*

- 이 규칙 하나로 두 문제가 동시에 풀린다. 반복 후렴구는 포인터가
  이미 첫 번째 반복을 지나쳤으니 두 번째 줄은 자동으로 두 번째
  반복에 물린다. 통째로 밀린 구간도 "몇 초 이내"라는 제한이 없어져
  실제로 얼마나 밀렸든 그대로 찾아낸다.
- 확신이 낮은 매칭(신뢰도 낮음)은 포인터를 아예 옮기지 않는다 —
  안 그러면 틀린 추측 하나가 그 뒤 모든 줄을 연쇄적으로 망가뜨릴
  수 있다(실제로 이 안전장치를 빼먹은 중간 버전에서 확인불가 줄이
  978→1043으로 오히려 늘어나는 걸 보고 알아챘다).
- 그래도 "신뢰도는 높은데 너무 멀리 떨어진" 매칭(예: 52초 차이)은
  자동 적용하지 않고 보고만 한다 — 우연히 같은 표현이 다른 데서도
  나온 것일 수 있어서다.
- 교정하는 과정에서 앞뒤 줄과 순서가 엉키면(드물게), 그 줄을 원래
  값 그대로 두는 대신 **앞 줄 바로 뒤로 살짝 밀어내고** "estimated"로
  표시한다 — 잘못된 값을 그대로 두는 것보다, 위치를 모른다는 걸
  솔직히 표시하는 쪽을 택했다.

## 만들면서 잡은 버그 2개 (모두 재검증하다 발견 → 백업에서 되돌리고 재작업)

- **포인터 과소비**: 처음엔 신뢰도가 낮은 매칭도 포인터를 옮겨서,
  운 나쁘게 튄 추측 하나가 그 뒤 모든 줄의 검색 범위를 밀어버렸다.
  → 포인터는 확신 있는 매칭에서만 옮기게 고쳤다.
- **끝 시각 잘라내다 시작 시각보다 작아짐**: 겹침 방지로 `end`를
  다음 줄 직전까지 줄이는 마무리 단계에서, 두 줄이 아주 바짝
  붙어 있으면 `end`가 `t`보다 작아지는 경우가 있었다(0.02초 차이로
  끝나는 두 줄 등). → 최소 길이(0.3초)를 보장하도록 고쳤다. 이
  버그의 흔적이 **27번 작업(오늘 이전)에서도** 2개 파일에 이미
  남아 있던 걸 이번에 같이 찾아 고쳤다(입시 스트레스, Last Stage — 두 곳 다 `end === t`인 무음 길이 줄이었다).

## 무엇을 만들었나

- **연주 중 `M` 키**: 가사 자막이 안 맞는다고 느끼는 순간 누르면,
  그 시점의 실제 시각(`Snd.time()`)과 그 순간 화면에 떠 있던 자막
  줄(과 그 줄의 저장된 시각)을 `P.lyricFlags`에 기록한다. 화면
  위쪽에 "표시했습니다 (N개째) — 그 줄 텍스트"라는 토스트가 잠깐
  떴다 사라져서 제대로 눌렸는지 바로 알 수 있다. 자막이 꺼져 있거나
  이 곡에 가사가 없으면 "표시할 가사 자막이 없습니다"라고 알려준다.
  - 왜 M인가: S·D·F·Space·J·K·L은 전부 6/7키 레인 건반이라 못 쓴다.
    이번에 F(내 음악 파일 열기)를 지우면서 F도 비긴 했지만 그것도
    레인 건반이라 못 쓰는 건 마찬가지다.
- **결과 화면(연주 완료 후)**: 이번 판에서 표시한 기록이 하나라도
  있으면 판정 내역과 다시 도전 버튼 사이에 새 상자가 나타난다.
  "가사 확인 표시 N개 — 아래 내용을 복사해서 전달하세요"라는 안내와
  함께, 곡 제목·확인 순간 시각·그때 뜬 줄·저장된 시각을 한 줄씩
  정리한 텍스트 영역과 "복사하기" 버튼이 있다. 버튼을 누르면
  클립보드로 복사하고(안 되는 환경이면 텍스트를 자동 선택해 둬서
  Ctrl+C로 복사 가능), 이 내용을 그대로 채팅에 붙여넣으면 된다.
- 곡 선택 화면의 "조작법" 안내에도 M 키 사용법을 한 줄 추가해
  두었다(추가 설정 안의 "가사 자막이 맞지 않는 순간이 있으면...").

## 검증한 내용

### 확인하지 못한 부분

# 32. 하이라이트 "느려졌다 팍 내려오는" 연출 재설계 — 자연스럽게, 후렴·드럼 진입에서

사용자 피드백: "순간 느려졌다 팍 내려와서 리듬이 꽂히는 것이 어색함.
드럼 치는 구간이나 노래의 하이라이트 가사 부분에서 자연스럽게."

## 어색했던 원인

- 기존 `buildRhythmRushes`/`rhythmScrollTimeAt`은 0.36초 안에서 속도를
  1배 → 0.3배 → 약 2배로 **순간적으로** 바꾸고, 3연타 드럼이면 타격마다
  다시 0.3배 ↔ 1.8배를 반복했다. 판 전체가 뚝뚝 끊기며 움찔거리는 느낌.
- 위치도 "드럼이 센 구간 안의 3연타"라서 곡의 전환점과 무관했다.

## 무엇을 바꿨나 (`index.html`)

- **위치**: 두 종류의 전환점만 고른다.
  1. 후렴 — 가사에서 2번 이상 반복되는 줄들이 묶음(줄 간격 1.5초 미만,
     2줄 이상, 또는 한 줄이 3번 이상 반복)으로 시작되는 줄의 시각.
  2. 드럼 진입 — `soundFlow`(2초 단위 드럼 세기)에서 앞 4초보다 1.5 이상
     커지고 곡 상위 30% 세기에 드는 구간의 시작.
  두 경우 모두 **착지 시각은 반드시 실제 채보 노트**로 맞춘다(크래시 >
  킥 > 스네어/탐, 동시치기 가점, 기준 시각에서 멀수록 감점). 센 노트가
  없으면 그 후보는 버린다(가사 싱크가 조금 틀려도 드럼 타격에 붙는다).
  간격 12초 이상, 곡 길이/32 개(2~6개)까지, 후렴 우선.
- **움직임**: 착지 한 마디 앞(BPM 기준 1.1~2초)부터
  속도 1 → (코사인으로 부드럽게) 최저 0.5~0.72배 → 착지 순간 최고 약 1.8배
  → 0.45초 동안 다시 1배. 속도가 한 번도 튀지 않는다(C¹ 연속).
  최고 속도는 전체 지연이 0으로 돌아오도록 계산식으로 정한다.
  잔잔한 곳은 얕게(0.72), 센 곳은 깊게(0.5) 가라앉는다.
- 판정 타이밍은 원래대로다 — 노트는 스크롤 함수와 무관하게 늘 자기
  시각에 판정선에 닿는다. 최대 지연은 약 0.41초로, 기존 그리기 여유
  (노트 0.62초·마디선 0.52초) 안이다.
- 쉬움 난이도·동작 줄이기 설정에서는 여전히 꺼진다.
- `startPlay`에서 `S.lyrics`와 `chart.bpm`을 넘기도록 호출부만 바꿨다.
  가사 없는 곡(War, 첫 산책, 가을의 질주)은 드럼 진입만 쓴다.

## 32-3. "쉬어가기" 추가 — 몰아치다가 후렴에서 잦아드는 곳은 느려졌다가 돌아온다

- 연출을 두 종류로 나눴다(`kind`).
  - `drop`(몰아치기, 기존): 후렴이 확 커지는 곳. 가라앉았다가 착지에서 쏟아짐.
    끝나면 시작 전 시간선으로 돌아온다(`net = 0`).
  - `rest`(쉬어가기, 신규): 직전 4초(0.5초 앞당겨 측정)가 곡 상위 30% 세기이고,
    후렴 시작에서 세기가 2.0 이상 떨어지는 곳(가사 없는 곡은 3.5 이상).
    반 마디 동안 0.68배로 느려져 한 마디 유지, 한 마디에 걸쳐 1배로 복귀.
    **따라잡으려고 빨라지지 않는다** — 대신 그만큼(`net`) 늦은 시간선으로 이어진다.
- 구간 구조를 일반화: `{kind, start, land, end, phases:[{t,len,a,b,d}], net, offset}`.
  `offset` = 앞 구간들이 쌓은 지연. `rhythmScrollTimeAt`은 해당 단계의 코사인
  속도 적분에서 `offset`을 뺀다. 판정은 여전히 영향 없음(노트는 늘 자기 시각에
  판정선에 닿음).
- 그리기 범위를 실제 시각 → **화면 시간**(`rhythmScrollTime(n.t) - scrollNow`) 기준으로
  바꿨다(노트·마디선). 느린 구간에서 멀리 있는 노트가 갑자기 튀어나오지 않게.
  연출 없는 곡은 화면 시간 = 실제 시각이라 동작이 전과 같다.
- 곡당 몰아치기 ≤ 3, 쉬어가기 ≤ 2, 합계 ≤ 3, 20초 간격.
- 결과 13/33곡: 몰아치기만 — Bass Control, 두 사람의 행복을 빌어, Last Stage,

## 32-4. 몰아치기를 "음원에서 잰 빡! 순간"으로만 — 사용자: "몰아치기가 안 맞음, 사람이 빡! 느끼는 부분만"

- 검증: `tools/test-keysound.cjs` 신규(실제 타격 찾기·화음·최대 길이·겹침 없음·게임 연결·33곡 파일 존재) — 테스트 9개 통과.

- 확인 못 한 것: 실제 귀로 듣는 느낌(분리 잔향·조각 경계의 자연스러움), 저사양 기기 메모리.

## 39. Bass Control 쉬어가기 제거 + 모든 곡 "치면 박자에 소리"

- Bass Control: rests는 이미 비어 있었고, 느려지는 건 몰아치기(38.4) 앞 브레이크 가라앉기(`from`)였다. 사용자 "쉬어가기를
  없애자, 곡과 안 맞음" → 드롭에 `"slow": false`(from 제거). `dropRush`는 slow===false면 가라앉지 않고 착지 직전
  inExpo로 곧장 몰아친다(`rush.noSlow`). find-drops.py `NO_SLOW`에 기록(다시 돌려도 유지). 테스트: 속도가 1배 아래로 안 떨어짐.
- 사용자 "모든 곡에 적용했나? 노트를 치면 음이 들리듯 엄중한 박자감": 측정해 보니 노트의 36%(발라드 60~70%)는 아래에
  드럼이 없어 키음이 거의 무음이었다.
  - `keysoundWindows`: 구간 첫 0.08초 최대 진폭 < 곡 75백분위의 15% → `w.quiet`. quiet면 `playKeysound`가 false →
    합성 타격음(곡 저음에 맞춘 음색). 빈 건반도 다음 노트가 quiet면 레인 드럼.
  - `Snd.hit(drum, songTime)`: songTime이 아직 안 왔으면 그 박자에 예약(전에는 음색 선택에만 쓰고 즉시 재생 — 예전 테스트의
    "노트 시각까지 지연하지 않는다"는 이번 요청과 반대라 뒤집음). press는 `target.t`를 넘김 → 일찍 치면 박자, 늦으면 즉시.
  - 자동 레인: 소리를 0.1초 앞서 예약(`n.autoSound`) — 프레임만큼 늦던 것 해소. 일시정지 시 아직 안 친 노트의 예약 표시를
    풀어 이어 할 때 다시 예약.
- 검증: 전체 테스트 통과(test-keysound quiet·합성음 예약, test-note-audio·test-empty-key-sound 새 규칙으로 갱신).
  헤드리스(두 사람의 행복을 빌어 HARD, 드럼 없는 전주): 72타 모두 소리 남(예전엔 무음), 일찍 친 4타는 박자에 예약, 콘솔 에러 없음.
- 확인 못 한 것: 실제 귀로 듣는 느낌. 드럼 외 악기(기타·보컬)를 키음으로 쓰는 것은 하지 않음(메모리·분리 품질 문제).

## 40. 멜로디 키음 — 멜로디 노트를 치면 노래·선율이 난다(발라드는 노래방처럼)

- 사용자: "멜로디에 맞춘 노트니 멜로디를 실행하면 되지 않나? 발라드는 노래방처럼". 드럼 없는 노트(전체 36%)가 맞춰진
  소리를 재 보니 보컬 30%·기타 악기(기타·피아노·신스) 34%·베이스 3%·뚜렷한 시작 없음 34%.
- 음원(`tools/make-stems.py`): 멜로디 = 보컬 + 기타 악기(**스테레오** — 기타·신스가 좌우로 넓어 모노로 빼면 반주에 반대 위상
  잔향이 남는다), 반주 = 원곡 − 모노 드럼 − 멜로디(베이스·잔향). 반주+드럼+멜로디 = 원곡(29.3dB, MP3 차이뿐).
  songs.json `stems.melody` 추가, 33곡 생성(stems 폴더 415MB). 이전 드럼 전용 반주·songs.json은 `_stems_backup_drumonly/`.
- 게임:
  - `loadPlayAudio`: 반주·드럼·멜로디 셋(멜로디 있으면 셋 다 있어야 함 — 하나라도 실패하면 원곡).
    `S.keyTracks = [드럼, 멜로디]`.
  - `keysoundWindows(notes, stems)`: 트랙마다 ±0.02초 실제 시작과 0.08초 최대 세기. 드럼이 있으면 드럼(src 0),
    없으면 멜로디(src 1), 둘 다 없으면 quiet(합성 타격음). 기준 = 곡 안 75백분위의 15%와 절대 0.02 중 큰 값.
    앞당김(프리롤) 드럼 4ms·멜로디 12ms(노래 첫소리가 부드러워 잘리지 않게). 구간 끝 = 같은 트랙의 다음 구간(최대 0.9초).
  - `Snd`: `keys = { tracks, windows }`, 트랙마다 자기 구간만 닫는 게이트(`keyNodes`). quiet 구간은 아무것도 닫지 않는다.
- 결과: 두 사람의 행복을 빌어 996구간 → 드럼 360·멜로디 611·합성 25(무음이던 70% → 2.5%).
  Break It Down 973 → 드럼 787·멜로디 184·합성 2. 자동 연주(0.02초 일찍)로 멜로디·드럼 조각이 박자에 예약됨, 콘솔 에러 없음.
- 메모리(연주 중, 4분 곡·48kHz): 반주 2ch + 드럼 1ch + 멜로디 2ch ≈ 230MB(원곡만일 때 92MB의 2.5배). 미리듣기 캐시는
  연주 시작 때 비운다. 약한 기기에서 부족하면 설정의 타격음 끄기 → 원곡만 읽는다.
- 확인 못 한 것: 실제 귀로 듣는 느낌(노래가 조각나 들리는지), 실제 저사양 기기 메모리.

## 42. 키음 방식 최종 — 트랙은 끊김 없이 흐르고 "크기"만 바뀐다(밀림·끊김 해소)

- 사용자: "가을의 질주도 약간 그런데 나머지는 처참할 듯. 끊기는 듯한 것, 밀리는 듯한 문제 해결 요청".
- 원인(조각 재생 방식의 구조적 한계): 친 순간 조각을 트니 늦게 친 만큼 소리 위치가 반주와 어긋나고(밀림),
  조각이 끝나고 다음 조각 사이·늦은 첫소리 앞이 비었다(끊김).
- 새 방식(`Snd`): 트랙마다 소스 하나를 두 갈래로 — base(구간 밖 1, 자기 노트 구간 안 `KEY_GHOST` 0.18 ≈ −15dB) +
  boost(친 구간에서 1 − GHOST). 소리는 늘 반주와 같은 시계·같은 위치 → 밀림 0, 끊김 없음.
  - `keyBoost(w, songS)`: 일찍 쳤으면 base가 작아지는 4ms 동안 같이 올려 합 1로 박자 그대로, 늦었으면 지금부터 fadeIn
    (드럼 2ms·멜로디 8ms). w.end까지 유지, 뒤 같은 트랙 구간(w.chain)을 못 치면 0.12/0.3초에 걸쳐 작아짐.
    앞 올림이 남아 있으면 그 크기에서 이어 간다(`kn.last`, `keyLevel`). 친 구간은 `keys.boosts`에 모아 이어 하기 때 다시 건다.
  - `keyArm(w)`(흐름 유지 보조): 콤보 중이거나 아직 놓친 적 없으면, 게임 루프가 0.1초 앞 구간의 첫소리를 박자에 맞춰
    0.08초(`KEY_GRACE`) 원래 크기로 열어 둔다 → 그 안에 치면 그대로 이어지고, 안 치면 0.04초에 작아진다.
    놓치면(콤보 0) 다음에 칠 때까지 열지 않는다(놓치면 빠진다 유지). 실측 남은 끊김 7번이 전부 "쉬었다 다시 시작하는

## 45. 몰아치기: 앞 노트를 다 친 뒤에 느려진다

- 사용자: "노트를 다 치고 느려져야 하는데 노트가 있다가 느려지니 헷갈릴 듯. 느려지는 타이밍엔 단일 노트를 다 치웠을 때".
  예전엔 착지 한 마디(브레이크) 또는 lead초 앞부터 느려져서 그 사이 노트가 내려오는 채로 느려졌다(타격 사이만 비웠다).
- `dropRush`: 느려지기 시작 = max(예정 시작, 착지 반 박 앞까지의 마지막 노트 끝 + 0.05초). 남는 시간이
  approach(가속 + min(½박, 0.3) + 0.15 ≈ 0.9~1.2초)보다 짧으면 착지 − approach에서 시작하고 그 안의 노트는 비운다.
  브레이크 유무 두 갈래를 하나로 합침(fromBreak 표시는 유지). 가라앉지 않는 몰아치기(slow:false)는 그대로.
- `addDropAccents`: 비우는 구간 = [느려지기 시작, 마지막 타격 + 반 박](예전엔 첫 타격 − 반 박부터). 그 앞에서 시작한
  긴 노트는 지우지 않고 꼬리를 느려지기 0.05초 앞에서 끝낸다(0.2초 미만이면 단일 노트).
- 실측: 몰아치기마다 느려지기가 앞 노트 0.02~0.4초 뒤에 시작, 비워지는 노트 1~7개(NC 다이노스 2~3개).
- 테스트: 촘촘한 노트(0.5초마다)에서 "느려지는 동안 오는 일반 노트 없음", 길이 approach~한 마디, 브레이크 테스트는
  노트 없는 브레이크로, 긴 노트 꼬리 자르기 추가. 전체 통과.

## 50. 곡 끝 무음 · 약한 기기 메모리 · 보통 레벨 다양화

- 곡 끝: `soundEndOf(buffer)`(끝에서 1024샘플씩 거슬러 평균 세기 −50dBFS를 처음 넘는 곳)를 반주·키음 트랙 모두에 재서
  `P.endAt = min(파일 길이, max(소리 끝, 마지막 노트 끝 + 판정창)) + 1.2`. 곡마다 결과 화면이 0~1.5초(평균 0.7초) 빨라짐.
  새 채보는 소리가 끝난 뒤 노트가 없다(예전 System 176.6 vs 175.5 문제 해소).

  대신 원곡(약 92MB)+합성 타격음. 알려 주지 않는 브라우저는 그대로, 읽기 실패 시 원곡 전환도 그대로.
- 보통 레벨: attack-chart.py `normal_level()` — 어려움 15→10, 14→9, 12~13→8, 11→7, 잔잔한 곡(NORMAL_CALM) 6.

## 52. 곡 끝 마무리 — "들리는 끝" 기준 + 0.5초 페이드

- −50dBFS 기준은 거의 안 들리는 페이드아웃·잔향도 소리로 쳐서, 귀로는 결과 화면까지 평균 1.6초·최대 4.6초(Bass Control)
  조용했다. Bass Control·깊은 밤은 그 안 들리는 꼬리에 노트까지 있었다.
- `soundEndOf`: 그 음원의 큰 소리(0.1초 묶음 세기 95백분위)보다 30dB 넘게 작아지기 전 마지막 곳(묶음마다 앞 2048샘플만 봄).
  `P.endAt = min(파일 길이 + 0.3, max(들리는 끝, 마지막 노트 끝 + 판정창) + 0.8)`, 마지막 0.5초(`P.fadeAt`)에
  `Snd.fadeOut()`으로 음악을 줄인다(일시정지하면 `P.fading`을 풀어 이어 할 때 다시 줄임).
- attack-chart.py `audible_end()`(같은 기준, 드럼+멜로디+베이스 스템): 그 뒤에는 노트·긴 노트 꼬리를 두지 않는다.
  해당 6곡(Bass Control·깊은 밤·스파이크·푸른 하늘 위로·우린 봄이야·G_Force) 채보 재생성.
- 결과: 들리는 끝 → 결과 화면 평균 0.9초·최대 1.3초(0.5초 페이드 포함). 테스트 test-song-end 갱신.

## 53. 채보 배치 개선 4가지 + 드럼 뼈대 우선

- 사용자: "모두 개선해 주고, 드럼은 웬만하면 채보로 작성해서 리듬감을 키우면 좋을 듯".
- 고르는 순서(attack-chart.py build): 가사 단어(꼭, 시간 순) → **드럼 뼈대(킥·스네어·크래시, 센 순서)** → 나머지(멜로디·하이햇).
  밀도 목표(레벨) 안에서 드럼이 멜로디·하이햇보다 먼저 들어간다(가사 단어만 목표를 넘어서도 넣는다).
- 레인: 스네어 자리 [5,1] → [5,1,4,2], 하이햇 [6,0] → [6,0,5,1]. 드럼·멜로디 모두 최근 2초 동안 덜 쓴 키부터.
- 같은 키 연타: 같은 레인 재사용 간격 0.18초 → 0.25초(또는 ½박).
- 한 손 연속: 한 손으로만 4번 넘게(0.3초 안 간격) 이어지면 다음 노트는 반대 손 먼저(멜로디는 거울 자리).
- 어려움 긴 노트: "누르는 동안 다른 노트 없음" 긴 노트 외에, 반대 손은 계속 치면서 누르는 긴 노트(0.5~1.6초)를
  박자의 5%까지. 그동안 누르는 손 쪽 레인엔 노트를 두지 않는다(`lock_side`). 쉬움·보통은 그대로.
- 결과(33곡 재생성, NC 동시 키 다시 적용, 레벨 갱신, 전체 테스트 통과):
  D·K 한 키 비율 25~29% → 18~19%, 레인 쏠림(변동계수) 0.45 → 0.22(어려움), 같은 키 0.25초 안 연타 7.6% → 0%,
  어려움 긴 노트 평균 4 → 36개(쉬움 28·보통 7), 한 손 연속 최대(긴 노트 누르는 동안 제외) 8~9 → 4타.
  센 킥·스네어에 노트가 있는 비율(11곡 표본) 쉬움 30%·보통 56%·어려움 82%. 레벨 분포는 그대로.
